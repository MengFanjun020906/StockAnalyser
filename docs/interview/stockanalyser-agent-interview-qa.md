## 0. 简历与开场

### 0.1 一句话介绍

针对传统股票分析中数据源分散、单次 LLM 结论不稳定且难以追溯的问题，我基于 LiteLLM 和自研 Agent 框架搭建了覆盖 A 股、港股和美股的智能分析系统，将多源数据获取、多步分析、选股决策和确定性风控串成统一链路，实现了单股分析与多候选选股，并让每个结论都能追溯到对应的数据、工具和规则。

### 0.2 60 秒项目介绍

这个项目的背景是，股票分析需要同时处理行情、K 线、资金流、新闻和基本面等异构数据。单纯让大模型一次性生成结论，容易出现数据遗漏、口径不一致、工具失败后仍强行下结论，以及结果无法复盘的问题。

为了解决这些问题，我基于 LiteLLM 和自研 Agent 框架实现了一套混合式分析架构。系统先识别用户是在做单股分析、持仓复盘还是多候选选股，再结合账户、持仓和风险偏好生成分析计划；执行阶段通过统一工具层获取多源数据，单股场景使用有界 ReAct 补齐证据，选股场景使用候选召回、逐股取证、组合配置、反方审查和 Judge 裁决的阶段化流程。对于评分、仓位和交易限制，则使用策略 4、缠论评分和 Risk Gate 等确定性规则约束模型结论。

最终，这套系统把原本分散的数据获取、分析和风控能力串成了统一的单股与选股链路。工具失败时能够记录缺失并降级，而不是编造数据；每次运行都会保存计划、工具调用、证据、耗时和最终决策，因此可以回放历史过程、定位 Badcase，并验证新策略接入前后的影响。

### 0.3 简历描述参考

**项目：StockAnalyser 智能股票分析与选股 Agent**

- 设计自研混合式 Agent 架构，组合确定性 Planner、有界 ReAct、多专家选股流水线、反方审查、Judge 和 Risk Gate，覆盖单股分析与多候选选股。
- 建设统一 ToolRegistry 和多数据源 fallback，接入行情、K 线、技术结构、资金流、新闻、基本面及可选 Graphiti 知识图谱，并用结构化证据卡管理来源、时效和缺失信息。
- 建设 Agent Trace 与恢复机制，落盘 Planner、工具调用、证据账本、阶段状态、LLM token/成本和最终报告，支持 Badcase 归因与历史任务续跑。
- 将策略 4 + 缠论 20 分制拆为“有 I/O 的快照构建器 + 无 I/O 的纯函数评分器”，以影子模式接入选股和单股链路，并通过确定性 Risk Gate 审计仓位上限。

## 1. 核心概念与架构设计

### Q1：Agent 和 LLM 的区别是什么？

LLM 是负责理解和生成的模型；Agent 是以 LLM 为决策组件，再加上目标、状态、规划、工具、记忆、执行循环和停止条件组成的系统。只调用一次模型生成股票分析属于 LLM 应用；模型能根据证据缺口选择工具、读取结果、继续取证并受风险规则约束，才是 Agent。

在本项目中，LLM 负责工具选择和证据综合，但 K 线计算、确定性评分、仓位上限和风险门由代码执行，不能交给模型自由发挥。

### Q2：Workflow 和 Agent 的区别是什么？

Workflow 的步骤和分支大多由开发者提前确定，优点是稳定、便宜、容易测试；Agent 会根据当前状态动态决定下一步，适合输入开放、证据缺口不固定的任务，但成本和不确定性更高。

本项目没有二选一，而是组合使用：选股的大阶段是 Workflow，阶段内部的工具选择和证据补全可以由 Agent 决定；数据截断、评分和风控始终是确定性 Workflow。这样只在确实需要自主决策的位置使用 LLM。

### Q3：为什么不全部做成 Workflow？

股票问题的意图、标的、持仓状态和数据缺口变化很大。固定流程要么漏证据，要么每次都调用全部昂贵工具。Agent 可以根据主假设、已有证据和失败结果选择必要工具；但交易约束不能依赖模型，所以仍保留确定性阶段。

### Q4：Plan & Execute 和 ReAct 有什么区别？

Plan & Execute 先生成较完整的步骤计划，再逐步执行，适合任务长、需要审计和并行的场景；ReAct 是“思考当前状态 -> 调工具 -> 观察结果 -> 再决定”，适合中途信息会改变路径的场景。前者全局性强，后者适应性强。

项目采用混合模式：Planner 先把 intent 映射为 capabilities、tools、风险检查和停止条件；单股执行再进入 ReAct 循环。选股链路则更接近显式的 Plan & Execute 阶段图。

### Q5：项目是单 Agent 还是多 Agent？

准确说是混合架构。默认配置支持单 Agent 执行内核；同时提供 Technical、Intel、Risk、Specialist、Decision 等多 Agent 编排模式。选股链路还包含候选专家、多维证据专家、反方审查和 Judge。不要简单回答“纯多 Agent”。

### Q6：多个 Agent 怎么通信？

项目不让多个 Agent 通过自然语言随意对话，而是让它们读写同一份结构化状态。这样可以明确知道每条数据由谁产生、被哪个阶段使用，也能避免前一个 Agent 的长篇回答直接污染后一个 Agent 的上下文。

项目根据运行场景使用三种状态对象：

- `AgentContext`：用于单股多 Agent 分析，保存股票、已获取的数据、各 Agent 的意见和风险标记。例如 Technical Agent 写入趋势判断后，Risk Agent 和 Decision Agent 可以直接读取。
- `SelectionRunContext`：用于多候选选股，保存候选池、市场环境、逐股取证、组合配置、Judge 结果、工具日志和证据账本。每完成一个选股阶段，就把结构化结果写入该对象。
- `AgentState`：用于专家图展示和 Trace，是经过 Pydantic 校验的专家共享快照，集中保存 EvidenceCard、专家意见、Judge 输入和 Risk Gate 结果。它主要负责把本轮专家状态结构化展示出来，不是选股主链路的运行总线。

单股多 Agent 的通信过程如下。Agent 按顺序运行，每个 Agent 都从 `AgentContext` 读取已有信息，再把自己的结构化结果写回去：

```text
用户问题：分析 贵州茅台 是否适合买入
                    |
                    v
        创建共享 AgentContext
        - stock_code: 600519
        - data: {}
        - opinions: []
        - risk_flags: []
                    |
                    v
Technical Agent 读取股票代码并调用技术工具
                    |
                    | 写入 data.trend_result
                    | 写入 opinions[technical]
                    v
Intel Agent 读取技术结果并补充新闻/事件
                    |
                    | 写入 data.news_context
                    | 写入 opinions[intel]
                    v
Risk Agent 读取行情、技术和新闻意见
                    |
                    | 写入 opinions[risk]
                    | 写入 risk_flags
                    v
Decision Agent 读取全部 data、opinions、risk_flags
                    |
                    v
              生成最终报告
```

这里没有发生“Technical Agent 给 Risk Agent 发一段聊天消息”。真正的通信介质是共享的 `AgentContext`，前一个 Agent 写入结构化字段，后一个 Agent 按字段读取。

完整字段示例见 [AgentContext 具体示例](stockanalyser-agent-glossary.md#7-agentcontext-具体示例)。

多候选选股的通信过程类似，但状态更复杂，因此使用 `SelectionRunContext` 保存每个阶段：

```text
候选专家
  | 写入 candidate_discovery
  v
SelectionRunContext
  |
  +-> 市场判断写入 market_regime
  +-> 逐股取证写入 single_stock_deep_dive
  +-> 组合配置写入 portfolio_allocation
  +-> 反方审查写入 adversarial_review
  |
  v
Judge 读取各阶段摘要并综合裁决
  |
  v
Risk Gate -> 最终选股报告
  |
  v
AgentState / expert_graph
  | 将证据卡、专家意见和 Judge 结果整理为结构化快照
  v
写入 Trace，供前端展示和事后复盘
```

选股主链路实际依靠 `SelectionRunContext` 中的阶段字段通信。`AgentState` 是主链路完成后的专家视图，不负责驱动前面的阶段流转。

在专家证据层，一组原始结果会按下面的方式压缩：

```text
工具原始结果
  -> EvidenceCard（单条标准化证据）
  -> ExpertEvidencePacket（某个专家的证据摘要）
  -> AgentState / expert_graph（形成可展示的专家证据视图）
```

例如分析 600519 时，趋势工具可能返回几百行均线、成交量和价格数据。系统先把它压缩成一张技术 EvidenceCard，保留数据来源、截止时间、趋势信号、反证和缺失字段；专家视图再把多张技术证据卡汇总成 ExpertEvidencePacket，只保留主要支持点、风险点、置信度和原始引用。主链路的 Judge 使用各阶段的结构化摘要完成裁决，ExpertEvidencePacket 则用于形成紧凑、可展示和可审计的专家证据视图。

### Q7：一个完整 Agent 工程有哪些模块？

至少包括输入与身份上下文、Planner、模型适配层、工具注册与权限、执行循环、状态与 Memory、结构化输出、容错与停止条件、评估、Trace/监控以及确定性 Guardrail。金融场景还需要数据时点、来源质量、回测和风险门。

### Q8：为什么采用“LLM + 确定性规则”的混合架构？

LLM 擅长理解开放问题、组合异构证据和生成解释，确定性代码擅长数值计算、边界判断和稳定复现。项目让 LLM 处理“看什么、如何解释”，让代码处理“怎么算、能不能执行”，从而降低幻觉和不可回放问题。

## 2. Memory 与上下文管理

### Q9：短期、中期、长期记忆怎么做？

项目没有强行用一个数据库表示所有 Memory，而是按生命周期拆分：

- 短期：会话消息保存在数据库中，运行时 Session 有 30 分钟 TTL，读取最近消息继续对话。
- 中期：历史分析摘要、报告和 Trace artifacts 保存一次任务的证据和结论，可供复盘或恢复。
- 长期：可选 `AgentMemory` 从历史分析和回测统计中读取个股记录、校准置信度和 Skill 权重；可选 Graphiti/Neo4j 保存时序事件关系。

`AgentMemory` 和 Graphiti 默认都不是无条件开启，因此面试时应说“项目已实现可选能力”，不要说每个请求都依赖长期记忆。

### Q10：跨会话记忆如何实现？

会话消息落数据库，使用相同 `session_id` 可以重新读取；进程内 TTL 只清理活跃 Session 对象，不删除数据库历史。分析级记忆则按股票代码、分析记录和回测结果查询。跨会话写入前应控制数据质量，避免把模型错误永久放大。

### Q11：Memory 和 RAG 有什么区别？

Memory 主要记录“系统或用户过去发生了什么”，强调身份、时间和生命周期；RAG 主要从外部知识中检索“回答当前问题需要什么”，强调召回相关性和证据来源。同一存储也可能承担两种角色，例如 Graphiti 中的历史事件既是长期记忆，也可作为当前选股的检索证据。

项目中，会话历史和分析校准更偏 Memory；新闻、基本面、历史行情和知识图谱搜索更偏 RAG/工具检索。

### Q12：一次请求的上下文如何组装？

项目按消息角色组装，而不是把所有内容拼成一段：System Prompt 定义职责和输出约束；会话历史提供短期记忆；预取数据提供行情和市场状态；`AgentUserContext` 与 Planner 计划提供任务、账户和执行约束；工具结果以 tool message 追加。多专家链路只传压缩证据包，不把所有原始 JSON 复制给每个 Agent。

### Q13：上下文窗口溢出怎么办？

项目采用“限制、压缩、引用”三层策略：限制历史消息数量和每个预取字段长度；把工具原始结果压缩为 `compact_tool_fact_card` 或 EvidenceCard，只保留关键字段；完整原始数据落 Trace artifact，通过 `raw_ref` 引用。研究型链路还有 token budget 和最大轮数，证据不足时保守结束。

### Q14：长期记忆对当前轮次有什么实际意义？

它不应该替代实时证据，主要用于校准。例如过去同一股票的判断结果可以作为背景，历史回测可修正某个 Agent 或 Skill 的置信度。样本不足时项目返回中性权重，避免少量历史造成过拟合。

### Q15：记忆生命周期如何设计？

会话记忆按活跃时间淘汰运行时对象；任务证据按 Trace 长期保留以便审计；EvidenceCard 带 `as_of`、freshness、valid_until 和 refresh trigger；Graphiti 是可重建投影，关系型数据仍是真源。敏感或错误信息应支持删除、纠错和重新投影，而不是只追加不治理。

## 3. Planning、Reflection 与状态流转

### Q16：多步规划具体怎么做？

Planner 先从 `AgentUserContext` 解析 intent、目标股票和持仓状态，再选择主维度和辅助 capabilities；每个 capability 映射到可用工具，并定义目的、预期结果、下游用途、失败降级和下一步。计划还包含 hypotheses、risk checks、stop conditions 和 replan policy，最终写入 `planner.json`。

当前 Planner 主要是确定性规划器，不依赖额外一次 LLM 生成计划，这降低了延迟和计划格式漂移。

### Q17：Reflection 模块怎么做？

项目没有让同一个模型泛泛地“再想一遍”，而是把反思具体化为反方审查、对抗式 Debate 和 Judge。反方阶段专门寻找证据冲突、追高风险和缺失项；Judge 综合正反证据与硬约束。这样 Reflection 有明确输入输出，也能在 Trace 中审计。

### Q18：规划失败或子 Agent 输出不对，如何 Replan？

Planner 定义有界 Replan 条件：核心工具失败、结果为空、强反证推翻假设，或主维度仍缺关键证据时，才允许换用同 capability 的替代工具；禁止同参数无信息重复调用和扩展无关能力域。证据仍不足就记录缺失并降低结论强度。

项目目前没有独立的 `Replanner` 服务节点。Replan policy 写在计划中，由有界执行循环和选股阶段 fallback 落实，这是面试时需要主动说明的实现边界。

### Q19：Agent 死循环怎么处理？

主要依靠硬预算而不是只靠 Prompt：限制 `max_steps`、每个专家的 LLM 轮数和工具数；设置整链路和单工具超时；缓存同工具同参数结果；标记不可重试错误；最后一步关闭工具并强制综合。如果仍拒绝结束，就返回明确错误，而不是无限继续。

### Q20：Planner -> Executor -> Replanner 状态机如何流转？

理想状态机是：Planner 生成计划和停止条件；Executor 执行当前步骤并写入 observation；Replanner 判断继续、替换工具、跳过辅助项或结束；满足停止条件后进入 Synthesis/Risk Gate。项目中 Planner 和 Executor 是显式模块，Replanner 逻辑分布在 plan policy、ReAct runner 和阶段 fallback 中。

### Q21：什么时候停止继续调用工具？

当主维度已经足以回答问题、新工具不会改变动作、出现足以否决强结论的反证，或关键工具失败且没有替代证据时停止。停止不等于强行给结论，证据不足可以输出 `wait`、`monitor` 或 `insufficient_data`。

## 4. Tool Use、MCP 与 Skill

### Q22：MCP 是什么？与 Function Calling 有什么区别？

[MCP](https://modelcontextprotocol.io/docs/learn/architecture) 是 Host、Client、Server 之间交换上下文的标准协议，包含生命周期、能力协商以及 tools、resources、prompts 等原语；Function Calling 是模型输出“调用哪个函数和哪些参数”的结构化交互能力。Function Calling 解决模型如何提出调用，MCP 解决外部能力如何被标准化发现、连接和管理，两者可以组合。

本项目核心链路目前不依赖 MCP，而是把 Python handler 注册到 ToolRegistry，再转换为 OpenAI 风格 tool schema。若未来接入 MCP，可以把 MCP `tools/list` 发现的工具适配进现有 Registry，而不改 Planner 和 Runner 的上层契约。

### Q23：MCP 和 Skill 有什么区别？

MCP 是连接外部工具和上下文的协议；Skill 是告诉 Agent “按什么业务方法分析”的可插拔能力包。项目中的交易 Skill 由 YAML 或 `SKILL.md` 定义，包含规则、说明、所需工具和适用市场状态，可以被路由、激活和按回测表现加权。

Skill 不能替代 Function Calling。Skill 可以要求“检查量价和均线”，但真正读取 K 线和计算指标仍需要工具或确定性代码。

### Q24：工具调用失败、参数错误或超时如何处理？

Runner 捕获异常并把失败、耗时、timeout 和结果预览写入工具日志；单工具和工具批次都有超时；同参数成功结果可复用，明确不可重试的失败不会盲目重试。数据层按数据源优先级执行 fallback，并返回 `ok/partial/stale/unavailable/failed` 和 `source_chain`。Planner 只允许在同一 capability 内补关键缺口，最终仍不足则降级结论。

### Q25：怎样让模型稳定输出符合 Schema 的 JSON？

组合使用明确的 JSON 契约、provider 的 `response_format`、Pydantic 校验、枚举和范围约束、确定性 fallback，以及 JSON 提取/修复。关键金融动作还要经过代码校验，不能因为 JSON 能解析就认为业务正确。项目的主报告解析支持从混合文本提取完整对象，并使用 `json_repair` 作为最后修复手段。

### Q26：多工具如何调度？

先由 Planner 选择 capabilities，避免把所有工具都暴力执行；一个 LLM turn 中的多个独立工具由 ThreadPoolExecutor 并行，返回后按原 tool call 顺序写回上下文；同参数调用使用缓存和去重。选股的多候选取证也限制 worker 数，昂贵工具通过阶段预算和专家 manifest 控制。

### Q27：如何控制工具权限和安全风险？

项目只允许调用 Registry 中注册的业务工具，不提供任意代码执行；专家还受 Python allowlist 和 YAML manifest 双重限制。工具参数可由上下文 guard 修正，调用结果进入证据层而不是直接执行交易。若增加有副作用工具，还需要审批、幂等键和更强沙箱。

## 5. 训练、SFT 与 Agentic RL

### Q28：这个项目做过 SFT 或 RL 吗？

没有。当前项目是 Agent 工程和业务规则系统，使用现成模型 API/LiteLLM 路由，没有训练自有基础模型。面试时应先明确这一点，再回答如果数据规模和成本证明有必要，会如何训练。

### Q29：什么场景用 SFT，什么场景用 RL/GRPO？

SFT 适合学习稳定格式、工具选择习惯、参数生成和业务术语；RL/GRPO 更适合存在可验证结果、需要优化长程策略和成本权衡的任务。对本项目，若工具调用格式仍不稳定可先做 SFT；只有积累大量可回放轨迹，并能定义收益、风险违规、工具成本和任务成功等可靠 reward 后，才考虑 RL。

### Q30：Agentic 训练的 Loss 怎么设计？

一种简单设计是把文本/结构化输出、工具选择与参数、最终任务结果分开：SFT 阶段对 assistant 的回答和 tool-call tokens 计算交叉熵；RL 阶段再用任务完成、证据正确性、风险违规、调用成本和延迟组成序列级 reward。权重必须防止模型为了少调用工具而跳过关键证据，或为了回测收益而违反风控。

### Q31：多轮对话中的 Tool 和 Think 如何计算 Loss？

常见做法是把 system、user 和 tool result 当输入并 mask loss，只监督 assistant 输出和 tool-call 参数。是否训练显式 reasoning 取决于数据合规和模型方案；本项目不会把隐藏思维链作为审计依据，审计的是计划、工具、证据和最终规则检查。

### Q32：Tool Use 数据如何构造？

可以从成功 Trace 抽取“上下文 -> 工具选择 -> 参数 -> 结果 -> 最终答案”，再加入参数缺失、超时、空结果、过期数据和 fallback 等难例。合成数据必须实际执行工具或用确定性校验器验证，不能只让另一个模型编一条看似合理的轨迹。还应控制模板多样性，按股票、市场状态、意图和失败类型分层抽样。

## 6. Evaluation 与 Badcase 排查

### Q33：如何评估 Agent 整体效果？

项目会分层评估，而不是只看最终回答：

- 任务层：intent 是否正确、Schema 是否通过、必需 artifact 是否齐全、任务是否完成。
- 工具层：成功率、超时率、fallback 比例、数据新鲜度、字段覆盖和来源质量。
- 证据层：结论能否追溯到 EvidenceCard、是否遗漏反证、是否存在过期或冲突证据。
- 决策层：Risk Gate 违规率、强结论在证据不足时的误触发率、Judge/人工一致性。
- 业务层：候选 T+1 质量、方向准确率、胜率、入场成交率、区间收益、最大回撤和基准对比。
- 系统层：端到端延迟、各阶段耗时、token、估算成本和恢复成功率。

### Q34：Badcase 如何快速归因？

先按链路分层，不直接改 Prompt。检查 `request.json/context.json` 判断输入和 intent；检查 `planner.json` 判断能力和工具是否被选中；检查 `tool_calls.json` 判断参数、超时、fallback 和数据质量；检查 evidence ledger 和阶段 JSON 判断压缩时是否丢字段；最后检查 Judge、Risk Gate、最终渲染和前端展示。每一步都有 artifact，能区分“没取到、取到了但没传、传了但模型误判、后处理覆盖错误”。

### Q35：如何区分检索、模型和业务数据故障？

检索故障通常表现为工具失败、空结果、超时或 source chain 降级；业务数据故障表现为工具成功但关键字段缺失、日期过期、价格量级异常或不同源冲突；模型故障表现为证据完整但输出不符合 Schema、引用错证据或结论与规则冲突。三者分别依赖工具日志、DataQuality/EvidenceCard 和输出校验定位。

### Q36：如何保证 Agent 准确率？

不能保证绝对准确，只能通过分层约束提高可靠性：多源证据与时点检查、结构化证据卡、反方审查、确定性评分和 Risk Gate、离线回放、真实入口测试和线上 Trace。金融场景还必须把“预测正确率”和“系统事实正确率”分开，后者应尽量接近确定性，前者只能用长期样本评估。

### Q37：高并发下如何优化成本和延迟？

当前实现已经使用独立工具并行、候选并行取证、结果缓存、预取复用、紧凑上下文、最大轮数、整链路/工具超时和多模型 fallback。进一步扩展时可增加异步 I/O、按 provider 限流、请求合并、分层缓存、便宜模型路由、昂贵阶段按需触发和离线预计算。优化时必须同时观察 P50/P95、失败率、fallback 质量和 token，不能只降低平均延迟。

### Q38：怎样做离线评估集？

从真实 Trace 中按 intent、市场、数据完整度、行情状态和失败类型分层采样，冻结 `as_of` 和输入数据，保存期望工具、禁止动作、关键证据与人工标签。回放时分别比较规划、工具、证据、决策和风险门，不只比较最终文本相似度。

## 7. 框架选型与工程优化

### Q39：LangChain 和 LangGraph 有什么区别？

[LangChain Agent](https://docs.langchain.com/oss/python/langchain/agents) 提供较高层的模型、工具和标准 Agent loop 抽象，适合快速搭建；[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) 是更低层的状态化编排 runtime，强调节点/边、持久化、durable execution、streaming 和 human-in-the-loop。当前 LangChain 的 Agent 架构本身构建在 LangGraph 之上。

### Q40：项目为什么没有使用 LangChain/LangGraph？

项目核心控制面是自研的，直接使用 LiteLLM、ToolRegistry、Pydantic 状态和阶段化流水线。原因是已有大量金融数据 fallback、证据压缩、确定性评分、风险门和特定 Trace 契约，需要精确控制每层语义；引入框架并不会消除这些业务复杂度。代价是超时、恢复、可观测和状态机都要自己维护。

如果未来需要大量跨进程长任务、人工中断恢复和动态状态图，LangGraph 的 durable execution 会更有吸引力；不应为了简历关键词而迁移。

### Q41：项目是否基于开源 Agent 框架二次开发？

不是基于 LangChain、LangGraph 或 Dify 二次开发。Agent 编排、Runner、ToolRegistry、证据协议和 Trace 是项目内实现；LiteLLM 用于统一模型调用，Graphiti 用于可选时序知识图谱。这属于复用底层组件，而不是套用一个完整 Agent 平台。

### Q42：Agent Sandbox 和 Kubernetes 调度是什么关系？

Sandbox 解决单个任务的代码、文件、网络和权限隔离；Kubernetes 解决容器的资源分配、扩缩容、故障恢复和调度，两者职责不同。可以用 Kubernetes 承载 Sandbox worker，但 Kubernetes Pod 本身不自动等于安全沙箱。

当前项目工具主要运行在应用进程和线程池中，使用 Docker 部署，但没有实现“每次工具调用一个强隔离沙箱”或生产级 Kubernetes Agent 调度。若引入任意代码执行，需要增加预热 worker、镜像分层缓存、资源限额、网络策略和任务级凭证。

## 8. 项目特有的高频追问

### Q43：如何防止金融幻觉？

第一，要求价格、财务、新闻和持仓必须来自工具，不允许估算；第二，工具结果携带 source、as_of、freshness、warnings 和 missing fields；第三，只把压缩证据交给模型，同时保留 raw artifact；第四，Fact Guard、确定性评分和 Risk Gate 检查模型输出；第五，证据不足时允许输出等待，而不是强行推荐。

### Q44：如何防止历史回放中的前视偏差？

所有行情和评分先按冻结的 `as_of` 截断，再计算指标；固定日线 lookback 和 EMA 预热元数据，未收盘周线标记 provisional，不参与正式评分。回测必须复用与线上相同的特征函数，不能另写一套“看起来一样”的公式。

### Q45：为什么把纯数学评分接入 Agent，而不是直接替代 Agent？

数学评分擅长稳定筛选和约束，但不能完整解释新闻、基本面、账户目标和证据冲突；Agent 擅长综合异构信息，但数值判断不够稳定。项目把评分结果作为结构化证据注入单股和选股链路，再由 Risk Gate 审计仓位上限，二者互补。

### Q46：为什么评分器拆成快照构建器和纯函数？

快照构建器负责 I/O、联网补 K 线、`as_of` 截断、周线重采样和缺失标记；纯函数只接受 snapshot 与 policy 做评分。这样可以独立测试数据时点和数学公式，也避免调用方自己拼十几个布尔值。对应说明见[个股综合评分体系](../modules/individual-stock-composite-scoring-system.md)。

### Q47：为什么先用影子模式？

新评分先写入 Trace、报告和 Risk Gate check，但不改变真实动作，可以验证覆盖率、分层单调性、历史回放一致性和误杀率。确认数据稳定后再逐步开启 clamp，比直接让新规则控制交易计划更安全。

### Q48：如何做到可审计和可恢复？

Trace 会保存请求、上下文、Planner、todo、事件流、工具调用、阶段状态、证据、LLM telemetry 和最终报告。恢复运行读取旧 artifact，生成 Planning Ledger 复用摘要，只复用仍有效的数据，过期证据重新验证。隐藏思维链不作为审计真源。

### Q49：为什么候选召回分不能直接当买入分？

召回阶段目标是提高覆盖率，只表示“值得进一步分析”；买入还需要逐股技术、消息、资金、基本面、账户适配、反证和 Risk Gate。把召回分直接映射为交易动作会混淆 recall 与 precision，也是选股系统常见错误。

### Q50：怎样处理数据源 fallback 的质量下降？

Fallback 不只是捕获异常，还要返回采用了哪个源、数据日期、缺失字段和是否 stale。下游根据 `status` 与 DataQuality 决定证据权重；关键数据只有过期缓存时不能伪装成实时成功。金融系统宁可输出 partial/unknown，也不能静默换成语义不同的数据。

## 9. 项目难点与真实 Badcase

### Q51：这个项目最难的问题是什么？怎么解决的？

这个项目最难的不是接入某个大模型或实现一次工具调用，而是：**在行情、资金、新闻和基本面等多源数据可能超时、缺失或口径不一致，且 Agent 链路较长的情况下，仍然保证最终金融结论有可靠证据、局部失败可以降级、整个过程可以追溯。**

这个问题难在三个方面：第一，工具返回成功不代表数据可用，结果可能已经过期、字段不全或来自降级数据源；第二，原始数据经过 Planner、工具执行、多专家和 Judge 后，关键字段可能在上下文压缩中丢失；第三，LLM 即使输出了格式正确的 JSON，也可能引用错误证据，或者在证据不足时给出过强结论。

我的解决方案分为四层：

1. **数据层**：统一工具返回状态，记录 `source_chain`、`as_of`、freshness、缺失字段和 fallback 原因，区分“工具执行成功”和“数据可以作为证据”。
2. **证据层**：将原始工具结果压缩为 EvidenceCard，只保留影响决策的指标、反证和数据质量，同时通过 `raw_ref` 保留对完整原始数据的引用。
3. **执行层**：Planner 明确主分析维度、工具计划、停止条件和 Replan 规则；Runner 使用最大轮数、超时、并行、缓存和失败降级，避免重复调用和死循环。
4. **决策与审计层**：策略评分、仓位上限和 Risk Gate 使用确定性代码；每次运行落盘 Planner、工具调用、证据账本、阶段结果和最终报告，并用真实 Trace 入口做回归验证。

最终效果是，系统不会因为一个数据源失败就直接中断，也不会把缺失数据包装成正常结论；出现 Badcase 时，可以快速判断问题发生在数据获取、上下文传递、模型判断还是后处理阶段。新策略也可以先通过影子模式进入 Trace，验证稳定性后再影响实际决策。

面试时可以压缩成下面这段：

> 项目最难的是保证长链路 Agent 在多源数据不稳定时仍然可靠。我的做法是统一数据质量协议，把原始结果转换成可追溯的证据卡，通过有界 Planner/ReAct 控制工具调用，再用确定性评分和 Risk Gate 约束最终动作，同时把每个阶段写入 Trace。这样局部工具失败时系统可以降级而不是编造结论，出现问题也能快速定位到数据、模型或后处理环节。

### Q52：如何权衡报告生成时间、分析深度和报告篇幅？

我会先区分两个问题：**生成时间主要取决于工具调用数量、数据源响应时间和 LLM 轮数；报告篇幅主要取决于交给模型的上下文和最终输出结构。** 把报告写短不一定能显著降低取数时间，盲目减少工具则可能损失关键证据。

项目采用分层预算来做这个 Trade-off：

1. **按任务决定分析深度**：单股问答、持仓复盘和选股使用不同计划；多 Agent 还支持 quick、standard、full 和 specialist 等深度，避免简单问题也执行完整链路。
2. **主证据优先**：Planner 区分主分析维度和辅助维度。实时价格、数据时效、核心技术结构和风险约束属于必需证据；重复指标、扩展新闻和图谱关系属于按需证据。
3. **控制执行成本**：独立工具并行调用，复用缓存和预取结果，并设置最大轮数、单工具超时、总时间预算和停止条件。新增证据已经不会改变最终动作时，就停止继续调用工具。
4. **分离报告和原始证据**：最终报告只保留结论、关键依据、反证和操作条件；完整工具结果、证据账本和阶段输出保存在 Trace 中。这样报告可以简洁，但不会牺牲审计信息。
5. **允许降级输出**：时间预算耗尽或非关键工具失败时，基于已有证据输出 partial 报告并说明缺失项；关键行情或风险数据缺失时，则降低结论强度，不能为了按时返回而给出强交易建议。

评估这个 Trade-off 时，我会同时观察端到端 P50/P95 延迟、工具调用数、token、关键证据覆盖率和报告可读性，而不是只追求报告更短或响应更快。

面试时可以简化为：

> 我不会简单地用“少调工具、少写内容”换速度，而是先把证据分成必需和可选两层。价格、时效和风险证据必须保留，辅助新闻和重复指标按任务需要调用；执行层用并行、缓存、超时和停止条件控制耗时，展示层只输出关键结论，完整证据留在 Trace。这样可以缩短用户等待时间和报告篇幅，同时不牺牲关键决策质量。

### Q53：如何保证数据的准确度？

金融数据的准确度不能只靠“多接几个数据源”，我会把它拆成**来源准确、时点准确、口径准确和计算准确**四个层面：

1. **来源准确**：每个结果记录数据源和 `source_chain`，按明确优先级选择主源与 fallback。不同来源冲突时不简单取平均，而是根据字段语义、更新时间和源质量选择，无法确认就标记冲突并降级。
2. **时点准确**：所有数据携带 `as_of` 和 freshness；历史回放先按冻结日期截断，未收盘周期标记 provisional，避免未来数据泄漏。过期缓存只能标记为 stale，不能伪装成实时数据。
3. **口径准确**：统一股票代码、交易日、币种、复权方式、百分比/比例和成交量单位；对 OHLC、价格量级、涨跌幅和必需字段做合理性校验。实时行情与历史行情口径不一致时，需要显式校准或拒绝合并。
4. **计算准确**：技术指标和综合评分使用确定性纯函数，线上分析与历史回测复用同一套特征函数；通过边界样例、缺失数据和固定 `as_of` 的单元测试验证，避免两套公式发生漂移。
5. **输出准确**：LLM 只能引用工具提供的事实，EvidenceCard 保留数据质量和原始引用；Fact Guard、Schema 校验和 Risk Gate 再检查最终输出。无法验证的数据返回 partial、unknown 或 missing，而不是让模型估算。

因此，项目保证的不是“所有外部数据永远正确”，而是每个数据都知道来自哪里、属于哪个时间点、采用什么口径、经过哪些校验；一旦无法确认，系统会显式降级，不让低质量数据悄悄进入强结论。

面试时可以简化为：

> 我把数据准确度拆成来源、时点、口径和计算四层。工具结果必须带 source、as_of、freshness 和 fallback 记录；历史数据按固定日期截断，单位和复权口径统一，关键指标由线上和回测共用的纯函数计算。不同源冲突时不盲目平均，无法确认就标记缺失并降低结论强度。这样虽然不能保证上游永不出错，但可以保证错误不会被静默放大，而且能够追溯和复现。

### Badcase 1：新增 Strategy4 后，最新 Trace 看不到评分

**现象：** 单元模块已经能计算 Strategy4，但真实单股 Trace 没有展示新评分。

**根因：** 这是端到端接线问题，不是单一公式问题：本地 K 线不足 520 根导致快照不完整；评分生成时机晚于 Agent 推理，模型看不到；后端 artifact 即使有字段，前端也没有对应展示。

**修复：** 单股入口允许联网补齐固定历史窗口，在 LLM 推理前预计算并注入 `trace_composite_verdict`，最终统一写入 `composite_verdict.json`，同时补齐同步、流式、历史 Trace 和 Web 展示测试。选股多候选仍只用本地数据，避免网络请求按候选数放大。

**总结：** Agent 新能力要验证“注册/计算 -> Planner/上下文 -> Runner -> artifact -> API/SSE -> 前端”整条链路，局部单测通过不代表用户可见。

### Badcase 2：工具函数可用，但 Agent 实跑没有调用

**现象：** 直接调用工具返回正确，真实 Trace 却没有该工具或专家报告说证据缺失。

**根因：** 工具可见性有多层契约：Registry 注册、Planner capability map、Runner 压缩 profile、单股 tool schema、专家 Python allowlist、YAML manifest 和 Prompt 渲染。缺一层都会出现“工具存在但 Agent 看不到”。

**处理：** 从 `planner.json` 和 `tool_calls.json` 开始查，再逐层检查白名单、manifest 和模型上下文；测试覆盖真实 API/Trace 入口，而不是只 mock handler。详细清单见 [Agent Trace 测试避坑清单](../modules/agent-trace-testing-pitfalls.md)。

## 10. 面试时容易说错的地方

- 不要说“项目完全是多 Agent”，应说“单 Agent 内核 + 场景化多 Agent/多专家的混合架构”。
- 不要说“实现了 MCP”，当前核心是自研 ToolRegistry；MCP 是可扩展方向。
- 不要说“做过 Agentic RL/SFT”，当前没有训练自有模型。
- 不要把 Graphiti 说成唯一数据真源；它是默认关闭、可重建、可降级的可选图谱投影。
- 不要说“Replanner 是独立节点”，当前是 policy + runner + 阶段 fallback 的分布式实现。
- 不要说“工具失败就自动重试三次”，项目强调错误分类、fallback 和有界补证，不做无差别盲重试。
- 不要把候选召回分、LLM 置信度、20 分确定性评分和回测胜率混为一个 score。
- 不要用模型隐藏思维链证明可解释性；应展示计划、工具参数、证据引用、规则检查和最终动作变化。
- 不要承诺“保证股票预测准确”，应区分事实正确性、系统可靠性和市场预测效果。

## 11. 面试前应补齐的数字

准备最近一批真实 Trace，至少统计以下数据，再把真实数字写入简历：

| 维度 | 建议指标 |
| --- | --- |
| 数据集 | Trace 数、单股/选股比例、市场与行情状态覆盖 |
| 任务质量 | intent 准确率、结构化输出成功率、完整 artifact 比例 |
| 工具质量 | 调用成功率、超时率、fallback 比例、stale 比例 |
| Agent 效率 | 平均/P95 轮数、端到端 P50/P95 延迟、平均 token 与成本 |
| 业务评估 | 候选命中率、方向准确率、入场成交率、收益、最大回撤、基准差 |
| 风险 | Risk Gate 拦截数、证据不足强结论率、人工复核推翻率 |

只有统计口径、样本窗口和 `as_of` 固定后，这些数字才适合出现在简历中。
