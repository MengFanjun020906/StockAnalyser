# Agent 方案托管与模拟盘跟踪开发、测试与验收规格

本文档面向后续执行 AI，是可分阶段落地的实现合同。目标是在现有 Agent Trace、`TradePlan`、`risk_gate`、Portfolio 和本地行情能力上建立可持续跟踪闭环。第一版只做模拟盘，不连接券商、不触发真实委托。

实施依赖：优先完成 [Agent 回测系统规格](agent-backtest-system-design.md) 的 P0-A 至 P0-C，验证公共 execution/ledger 内核。托管复用相同的交易规则、费用、资金预留和成交语义，通过实时 clock/data adapter 接入；不得另建一套互相矛盾的撮合器。本文件的生命周期/页面设计继续有效，执行与资金语义以回测系统规格为准。

## 现状与依据

- Trace 已能从 Judge/选股裁决生成结构化计划并执行确定性 `RiskGateEvaluator`，但计划没有独立、长期有效的托管实体。
- `TradePlan` schema 位于 `src/schemas/agent_signal.py`；`agent-user-context-plan.md` 阶段 G 已定义计划状态、快照、模拟委托日志和反馈方向。
- 仓库已有 PortfolioService/持仓账本，以及 `src/services/agent_entry_execution_backtest_service.py` 的离线入场回放。托管不能把虚拟仓位写进真实 Portfolio 交易账本，也不能把离线回测冒充实时托管。
- 详细背景参考 `docs/plans/agent-user-context-plan.md` 阶段 F-G 和 `docs/plans/agent-entry-execution-backtest-plan.md`。本文件定义首期可执行范围；如旧计划与本文件状态规则冲突，以本文件为准。

## 目标和非目标

首期目标：用户在 Trace 对一个结构化计划明确选择“开始模拟托管”后，系统固定计划快照、记录虚拟订单和成交、按可用行情更新持仓/触发状态、保留偏离原因，并在用户退出或规则退出后生成可审计反馈。

非目标：真实交易、自动把托管仓位并入真实账户、保证成交、分钟级高频托管、自动调参/改写生产 Prompt、以 LLM 代替确定性规则、把普通 Markdown 报告猜测性解析成计划。缺少有效结构化 `TradePlan` 或 `risk_gate` 结果时不得创建可执行托管。

## 状态与数据合同

建议独立于 Portfolio 账本新增 `AgentPaperPlan` 聚合及 SQLite 持久化，优先沿用项目的存储初始化/事务模式，不要把复杂 JSON 文件散落到 Trace 目录。至少保存：

- 身份/来源：`plan_id`、`source_trace_id`、`source_session_id`、`symbol`、市场、创建/更新时间、schema 版本。
- 冻结快照：原始 `TradePlan`、Judge 结论、Risk Gate 输入输出、画像快照、关键证据引用、当时行情锚点。原快照不可被后续 Trace 覆盖。
- 托管状态：`pending_approval -> active -> monitoring -> exit_pending -> closed -> reviewed`，并支持 `rejected`、`invalidated`、`expired`、`paused` 终态/暂停状态。状态变化必须通过服务层校验并记录事件，不接受前端任意设置状态。
- 执行账本：虚拟订单、部分成交、撤销/拒绝、数量、成交价格、时间、费用/滑点假设版本、现金/持仓快照。明确区分计划触发价、模拟成交价与行情观测价。
- 跟踪记录：每次检查的行情时间戳/来源/质量、规则评估、未触发原因、偏离项、状态转移和错误。行情缺失或过期时记录 `unknown`，不得推断“未触发”。
- 退出与反馈：退出原因/手动退出者、实现收益、最大有利/不利变动（MFE/MAE）、持有时长、计划命中/偏离摘要、评价窗口及数据完整性。

交易状态更新需具备幂等键（plan + 触发规则 + 行情/调度检查周期），并以事务或 compare-and-set 防止并发重复成交。所有金额/数量需明确精度与市场最小交易单位；沿用现有市场/证券规则服务，不为其他市场扩展范围。

## 第一阶段实现顺序

1. 盘点 `TradePlan` 字段是否足够表达限价区间、有效期、止损/止盈、目标仓位、退出规则；优先适配现有 schema，只有缺失的机器可执行语义才做版本化扩展。新增字段必须向后兼容。
2. 新增 repository/store 和 service：创建计划前校验来源、状态、标的、有效期、Risk Gate；用户显式确认后激活；所有命令和转移写审计事件。
3. 实现确定性的模拟撮合器。首版写清“检查频率、价格取值、同一根 K 线同时触发止损与止盈时的保守优先级、跳空、涨跌停/停牌、费用滑点、T+1 限制”。不能用日线 OHLC 伪装盘中先后顺序；无法判定先后则按文档确定的保守规则记录歧义。
4. 接入可重试的调度检查。单标的/单计划失败不能阻断其他计划；重复执行必须幂等；行情 provider 失败只产生数据缺失记录，不更新仓位或状态。
5. 增加只读查询、显式动作 API（启动、暂停、恢复、退出）和用户可见托管页面/Trace 入口。写操作需身份校验、授权和 CSRF/现有 API 安全约定；操作返回最新状态。
6. 退出时生成反馈，并可由现有离线复盘/入场回测消费；首期反馈只存储和展示，不自动改变候选权重、风险规则或线上决策。

## API 与交互要求

按仓库 API 命名规范设计，不预设强行复用某个端点。至少覆盖：托管列表/详情、创建或确认托管、暂停/恢复、手动退出、检查记录/订单记录。请求必须携带幂等键或服务端生成可重试语义；列表支持状态、标的、账户（若模型需要）过滤和分页。

Trace 在风险闸门通过且计划可执行时给出“保存为模拟计划/开始托管”明确动作；闸门阻断、计划无效或数据不足时禁用并展示确定性原因。页面展示计划快照、状态、虚拟仓位、最新行情时间、偏离、退出条件和运行错误。任何自动执行含义都必须明确标为模拟盘。

## 测试与验证

后端单测：状态机允许/拒绝转移；Risk Gate 阻断时不能激活；快照不可变；同一幂等事件重复提交不重复成交；事务回滚；部分成交、跳空、双触发歧义、停牌/涨跌停、T+1、过期、缺价/陈旧价、手动暂停/退出、调度异常隔离；MFE/MAE 与费用计算边界。

API 测试：未认证/无权限写操作拒绝；创建、列表、详情、状态动作与错误码契约；非法输入、重复请求、并发动作；旧 `TradePlan` payload 仍可读取。

Web：托管入口状态、空/加载/错误状态、闸门阻断、暂停恢复确认、退出确认、日志/偏离展示和小屏布局；覆盖 API mock 的页面测试。必要时增加一条 Playwright 主流程：Trace 计划 -> 人工确认 -> 托管详情 -> 手动退出。

按改动面执行：`rtk pytest tests/test_agent_paper_plan* tests/test_agent_paper_execution* tests/test_agent_paper_plan_api.py`（执行阶段按实际文件名调整）、`rtk python -m py_compile <changed_python_files>`、Web `rtk npm run lint` 和 `rtk npm run build`；合并前执行 `rtk ./scripts/ci_gate.sh`。测试不可只断言 mock 调用，须检查持久化结果和重启后可恢复。

## 验收条件

- Trace 产生的合格计划可被用户明确启用托管，重启后状态、快照、订单和记录仍存在。
- 模拟成交不污染真实 Portfolio 持仓/现金/交易流水。
- 计划偏离、行情缺失、失效、退出均有可追溯记录；重复检查不会重复成交。
- 风控不通过/计划过期/行情不可用时不会发生模拟成交或伪造正常状态。
- 用户能查看并手动暂停、恢复和退出；所有动作经过服务端状态校验。
- 无自动策略学习、真实下单或跨市场扩展。

## 交付说明与回滚

同步更新托管专题文档、`docs/CHANGELOG.md` 扁平 `[Unreleased]` 项和 API spec（如 API 发生变化）。迁移必须可重复，回滚时保留历史表但关闭入口/调度，不删除用户托管记录。交付说明列出撮合假设、数据源/新鲜度、测试覆盖和未覆盖的盘中成交语义。
