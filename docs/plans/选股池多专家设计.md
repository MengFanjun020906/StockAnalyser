# 选股池多专家设计

本文档定义 L1 候选发现阶段的多专家架构，目标是让不同维度的候选发现逻辑解耦、可并行、可独立迭代，并为后续"条件入场"判断提供结构化证据。

## 架构总览

```
用户选股请求
    -> CandidateExpertOrchestratorV2
        -> [并行执行]
            -> 技术专家 LLM     只用行情/趋势/结构工具
            -> 低位启动专家 LLM 只用位置/拐点/预期差工具
            -> 资金专家 LLM     只用资金流/龙虎榜/热榜工具
            -> 基本面专家 LLM   只用财务/估值/业绩工具
            -> 消息事件专家 LLM 只用公告/新闻/事件工具
            -> 板块主题专家 LLM 只用板块/行业/主题工具
        -> 汇总器
            -> 去重、共振加分、位置因子、拥挤惩罚、冲突标记、硬风险过滤
            -> 输出 L1 候选池
```

## 核心设计

### 1. 专家模块化

每个专家是独立模块，不在一个 orchestrator.py 里混写逻辑。

目录结构：

```
src/agent/candidate_experts/
  orchestrator_v2.py          # 编排入口
  runtime.py                  # 并行执行、超时、缓存
  schemas.py                  # 统一输出 schema
  cache.py                    # 专家结果缓存
  prompts/
    technical.py
    capital.py
    fundamental.py
    news_event.py
    sector_theme.py
    aggregator.py
  experts/
    base.py                   # 专家基类
    technical.py
    capital.py
    fundamental.py
    news_event.py
    sector_theme.py
```

每个专家只负责：

- 定义自己的 system prompt
- 定义自己的工具白名单
- 跑一次 bounded tool-calling expert run
- 输出统一 schema

### 2. 工具白名单隔离

每个专家只能调用本维度工具。工具白名单定义在各专家模块内。

示例（`experts/capital.py`）：

```python
CAPITAL_TOOLS = [
    "get_capital_flow",
    "get_tushare_moneyflow_ths",
    "get_tushare_moneyflow_dc",
    "get_tushare_dragon_tiger_list",
    "get_tushare_dragon_tiger_inst",
    "get_tushare_limit_list_ths",
    "get_tushare_limit_step",
    "get_tushare_hot_rank",
    "get_stockapi_popularity_rank",
    "get_stockapi_hot_money_activity",
]
```

技术专家不能调用基本面工具，基本面专家不能调用资金流工具。这样专家意见才干净，后面汇总时才能判断"这是资金面支持"还是"基本面支持"。

### 3. 候选来源种子

每个专家从**共享种子池**出发，而非从零扫全市场。

种子池来源（按优先级）：

1. 用户自选股（如果有）
2. 强势来源种子：当日涨停板/热榜快照、强势板块成分股、AlphaSift/Sequoia 强势候选
3. 低位来源种子：基本面预计算里“成长改善但估值未扩张”的股票、120 日区间低位附近且最近首次放量转强的股票、前高/平台压力位被多次试探但尚未有效突破、且下方存在明显震荡换手与承接结构的股票、板块中“龙头已涨但二线补涨尚未充分演绎”的成分股。
4. 固定 fallback seed pool（只用于兜底观察，不参与策略评分）

专家职责是**筛选和解释**，不是发现全新标的。这样可以：

- 控制工具调用范围
- 保证专家输出有据可查
- 降低 LLM 幻觉风险

### 3.1 目标拆分：强势延续 vs 低位启动

如果用户真实意图是“低价买入，然后后面更容易涨”，候选池不能只偏向已经走强、已经上热榜、已经板块领涨的股票。

因此 L1 候选池要同时覆盖两类目标：

| 类型 | 目标 | 典型来源 | 主要风险 |
| --- | --- | --- | --- |
| 强势延续型 | 已经走强，但还未透支，适合顺势等待条件入场 | 热榜、强势板块、趋势突破、资金共振 | 追高、拥挤、次日分歧 |
| 低位启动型 | 仍处中低位，但已经出现拐点证据，适合低位潜伏或等确认后入场 | 低位放量、基本面改善、预期差修复、板块补涨 | 抄底抄在下跌中继、拐点假突破 |

硬要求：

- 候选池必须保留两类候选，而不是只输出“最热”的一类。
- 任何低位候选都不能仅因为“跌得多/价格低”入池，必须有至少一条可复核的“开始转强”证据。
- 任何强势候选都不能因为“涨得好/热度高”自动排在前面，必须经过拥挤风险和追高风险检查。

### 4. 单次专家执行边界

每个专家内部限制：

| 参数 | 值 |
| --- | --- |
| max_llm_rounds | 3 |
| max_tool_calls | 6 |
| timeout | 30s（单专家） |
| output_candidates | 2-5 |

流程：

```
system prompt + 种子池
    -> LLM 决定调用本维度工具
    -> 工具结果返回
    -> LLM 输出 JSON
```

如果模型没有调用工具直接输出候选，应判为 `partial` 或 `invalid`，除非 prompt 明确允许使用预注入的本地候选快照。

### 5.1 新增：低位启动专家

如果系统目标包含“低位买入然后更容易涨”，需要单独增加一个 `early_turn_expert` / `low_base_breakout_expert`，不能只靠现有技术专家顺带覆盖。

这个专家只关注一件事：

> 股票是否仍处于相对低位，但已经开始出现“下跌结束 -> 横盘 -> 资金回流 -> 首次转强”的拐点信号。

建议目录：

```text
experts/
  early_turn.py
prompts/
  early_turn.py
```

建议工具白名单：

- `get_realtime_quote`
- `analyze_trend`
- `calculate_ma`
- `get_volume_analysis`
- `analyze_price_structure`
- `get_capital_flow`
- `get_stock_info`
- 可选：板块/行业强度工具，但只允许作为验证，不允许它主导结论

这个专家的入池规则应显式检查：

1. **位置仍不高**
   - 相对 60/120 日区间仍处中低位
   - 距离长期压力位仍有空间
   - 不属于短期已经连续大涨后的高位拥挤区
2. **已经出现转强拐点**
   - 首次站回关键均线
   - 首次放量突破短平台
   - 回踩不破后重新放量
   - 主力资金由流出转为流入
   - 前高/平台压力位被 2-3 次试探但都没有明显放量回落，说明上方抛压在被逐步消化；若随后放量越过，更适合作为“潜在突破前夜”候选
3. **预期差而非纯弱势**
   - 基本面改善、行业景气改善、业绩修复、订单/政策催化开始出现
   - 价格尚未完全反映这些变化
4. **必须能说清失败条件**
   - 跌回平台下沿
   - 放量失败后缩回
   - 资金回流只有一天、无持续性
   - 板块环境与个股拐点不共振

这里要特别区分两种形态：

- **可入池的多次试探**：多次冲击同一压力位，但下方有横盘/震荡换手，回落幅度收敛，说明筹码在吸收，一旦放量越过容易进入加速段。
- **不应入池的反复冲高失败**：每次冲高后都长上影、大幅回落、量价失真，说明上方抛压没有被消化，只是弱势反弹。

这个专家的输出 `reason` 不能写成“位置低、可能补涨”，而必须写成：

- 低位证据
- 转强证据
- 仍未透支的证据
- 失败条件

示例：

```json
{
  "expert": "early_turn_expert",
  "dimension": "early_turn",
  "status": "ok",
  "candidates": [
    {
      "code": "300000",
      "name": "示例股票",
      "score": 84,
      "confidence": 0.68,
      "stance": "support",
      "reason": "股价仍处 120 日区间中低位，但近 5 日首次放量站回 MA20，且主力净流入由负转正，属于低位启动而非高位追涨。",
      "evidence": [
        {"tool": "analyze_trend", "summary": "首次站回 MA20，趋势由弱转中性"},
        {"tool": "get_capital_flow", "summary": "主力净流入转正"},
        {"tool": "analyze_price_structure", "summary": "平台整理后向上试探"}
      ],
      "risks": [
        {"type": "false_breakout", "summary": "若重新跌回平台下沿，则视为假启动"}
      ]
    }
  ]
}
```

### 6. 并行执行与失败处理

6 个专家**并行执行**，总超时 45s。

失败处理策略：

| 状态 | 处理 |
| --- | --- |
| 单专家超时 | 记录错误，跳过该专家，继续汇总 |
| 单专家报错 | 记录错误，跳过该专家，继续汇总 |
| 3/6 及以上专家失败 | 汇总器继续，但输出 `status: partial` |
| 6/6 专家失败 | 降级到 fallback seed pool |

失败的专家仍会生成一个空 packet：

```json
{
  "expert": "capital_flow_expert",
  "dimension": "capital",
  "status": "timeout",
  "errors": ["capital_flow_expert timeout after 30.0s"],
  "candidates": []
}
```

### 7. 汇总器逻辑

汇总器不直接调用维度工具，只看专家 packet：

```
technical_packet
early_turn_packet
capital_packet
fundamental_packet
news_event_packet
sector_theme_packet
```

汇总器职责：

1. **去重**：同一股票多专家推荐时合并
2. **共振加分**：多专家支持时提升 `signal_score`
3. **位置因子**：区分“高位强势延续”与“低位启动”
4. **拥挤惩罚**：防止热度过高的股票因为多专家都看见而自动排前
5. **冲突标记**：识别矛盾证据（如资金强但基本面差），标记为 `risk`
6. **硬风险过滤**：ST、退市风险、停牌等直接排除
7. **容量控制**：每个维度入选数量上限

#### 共振加分规则

| 支持专家数 | 加分 | 说明 |
| --- | --- | --- |
| 1 | 0 | 单维度支持 |
| 2 | +8 | 双维度共振 |
| 3 | +15 | 三维度共振 |
| 4+ | +20 | 强共振，标记为 `multi_expert_recall` |

额外加分：

- 技术 + 资金共振：+5（最强组合）
- 基本面 + 消息共振：+3（基本面验证）
- 低位启动专家 + 资金专家共振：+4（低位启动得到真实承接验证）
- 低位启动专家 + 基本面专家共振：+3（预期差修复更可信）

#### 位置因子与上涨赔率

如果目标是“低位买入，然后后面更容易涨”，汇总器不能只按“谁更热、谁共振更多”排序，还要显式计算：

```text
position_score      = 当前所处价格位置是否仍有空间
timing_score        = 是否已经出现启动信号
asymmetry_score     = 上行空间 / 下行风险是否更优
crowding_penalty    = 是否已经过热、拥挤、追高
```

建议最终候选分拆成：

```text
candidate_score = base_score
    + resonance_bonus
    + position_score
    + timing_score
    + asymmetry_score
    - conflict_penalty
    - crowding_penalty
    - risk_penalty
```

解释：

- `position_score` 高：说明还没涨很多，位置更舒服
- `timing_score` 高：说明不是纯便宜，而是已经开始转强
- `asymmetry_score` 高：说明“上涨空间大于下跌风险”
- `crowding_penalty` 高：说明虽然强，但太拥挤，不适合低吸

这一步是“低位潜力股”和“高位热门股”最大的分水岭。

#### 冲突标记规则

以下情况标记为 `conflict_risk`，不直接排除但加入风险说明：

| 冲突类型 | 说明 |
| --- | --- |
| 资金强 + 基本面弱 | 短期炒作风险 |
| 技术强 + 消息负面 | 利空未兑现风险 |
| 板块强 + 个股资金弱 | 跟风补涨风险 |

#### 追高/拥挤降权规则

以下情况不一定直接排除，但必须显著降权，避免系统把“已经涨起来的热股”误当成“低位潜力股”：

| 情况 | 处理 |
| --- | --- |
| 距 20/60 日高点过近，且最近 3-5 日涨幅过大 | `crowding_penalty` 提高 |
| RSI/乖离率/短线量价明显过热 | 降级为 `strong_watch` 或 `wait` |
| 热榜、龙虎榜、板块热度同时过高 | 标记为 `chase_risk` |
| 板块强，但个股已连续拉升、没有舒服回撤位 | 不得排在“低位启动型”前列 |
| 价格位置仍低，但没有拐点证据 | 不得因“便宜”加分 |

### 9. 缓存策略

专家结果支持同日缓存，减少重复 LLM 调用：

| 维度 | 缓存 TTL | 说明 |
| --- | --- | --- |
| 技术 | 交易日内 | 盘后数据不变 |
| 资金 | 30 分钟 | 盘中数据会变 |
| 基本面 | 1 天 | 财报周期长 |
| 消息 | 1 小时 | 公告可能更新 |
| 板块 | 30 分钟 | 板块强弱盘中变化 |

缓存 key：`{expert}:{market}:{date}:{seed_hash}`

缓存失效条件：

- 种子池变化
- 用户强制刷新
- 超过 TTL

## 与 wait 校准方案的关联

多专家输出的字段直接流入后续"条件入场"判断：

### 数据流转

```
多专家候选发现
    -> candidates[].confidence      -> 候选分计算
    -> candidates[].stance          -> 支持/反对判断
    -> candidates[].evidence        -> 证据卡片渲染
    -> candidates[].risks           -> 风险标记
    -> quality.multi_source_count   -> 共振加分
    -> quality.resonance_distribution -> 条件入场强度判断
```

### 条件入场判断规则

| 条件 | 结果 |
| --- | --- |
| 3+ 专家支持 + 无硬风险 + 有止损条件 | `conditional_open` |
| 2 专家支持 + 高候选分（≥85） | `conditional_open` |
| 高候选分但缺止损/失效条件 | `strong_watch` |
| 单专家支持或 weak confidence | `plain_wait` |

对于“低位买入”目标，再补一条：

| 条件 | 结果 |
| --- | --- |
| 低位启动专家支持 + 资金/技术至少一维共振 + 无追高惩罚 | `conditional_open` 候选优先 |
| 仅低位、但没有启动信号 | 不得升级为 `conditional_open` |

### 候选分计算公式

```
candidate_score = base_score
    + resonance_bonus           # 共振加分 0-20
    + position_score            # 低位空间 0-10
    + timing_score              # 启动确认 0-10
    + asymmetry_score           # 风险收益比 0-10
    + confidence_avg * 10       # 平均置信度 0-9
    - crowding_penalty          # 拥挤/追高扣分 0-15
    - conflict_penalty          # 冲突扣分 0-10
    - risk_penalty              # 硬风险扣分 0-20
```

高候选分阈值：

- ≥90：强候选，优先输出条件入场
- 80-89：中候选，需补足证据
- <80：弱候选，默认 `plain_wait`

## 与现有实现的关系

短期不删旧逻辑，加一个 v2 模式：

```
AGENT_CANDIDATE_DISCOVERY_MODE=deterministic | llm_expert_committee
```

默认先不开，Trace 测通后再切。

旧的 provider 保留为工具或 seed source：

- AlphaSift -> 种子池 + 策略专家可调用工具
- Sequoia -> 种子池 + 技术专家可调用工具
- fundamental snapshot -> 种子池 + 基本面专家可调用工具
- TuShare/StockAPI -> 各维度工具

## 第一版专家

第一版 5 个专家：

1. `technical_expert` - 行情/趋势/结构
2. `early_turn_expert` - 低位启动 / 拐点 / 预期差
3. `capital_flow_expert` - 资金流/龙虎榜/热榜
4. `fundamental_expert` - 财务/估值/业绩
5. `news_event_expert` - 公告/新闻/事件
6. `sector_theme_expert` - 板块/行业/主题

如果资源不够，`early_turn_expert` 可以放在第二批，但从“低位潜力股发现”的业务目标看，它比单纯再强化已有热点候选更重要。

## 测试策略

### 单专家测试

- Mock 工具返回固定数据
- 验证输出 schema 合规
- 验证工具白名单隔离（调用非白名单工具应失败）


## 风险与护栏

- 不能因为共振加分就把弱候选升级为 `open`
- 不能绕过硬风险过滤（ST/退市/停牌）

- 缓存不能跨交易日复用

## 接入现状 & 单次运行覆盖

- **接入入口**：`api/v1/endpoints/agent.py::AgentTraceRunRequest.candidate_discovery_mode`，可选值 `deterministic` / `llm_expert_committee`，默认 `None`（按 `.env` 的 `AGENT_CANDIDATE_DISCOVERY_MODE` 决定，再回落 `deterministic`）。
- **facade**：`src/agent/candidate_experts_v2/committee.py::run_committee_discovery`。当前仅资金面 `CapitalFlowExpert` 接入 LLM，其它维度仍跑 deterministic `discover_watchlist_candidates` 全量结果，并把资金面 LLM 证据 attach 到对应候选 `llm_expert_evidence.capital`。
- **流程分流**：`src/agent/stock_selection.py::_run_candidate_discovery_tool` 根据 `SelectionRunContext.candidate_discovery_mode` 分流；committee 抛异常时自动回退 deterministic 并 emit `selection_candidate_discovery_mode` 事件携带 `fallback=True`，保证 LLM 失败不拖垮整条流水线。
- **单次生效**：request 优先级 > env > 默认。前端 `AgentTracePage` 配置面板的"候选发现模式"下拉持久化到 `localStorage.dsa.candidateDiscoveryMode`，每次 `traceStream` 调用按当次值提交，不修改进程默认。
