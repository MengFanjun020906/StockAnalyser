# 选股链路重构 · 详细实施方案(召回 / 席位 / 深入探究)

## Context(为什么做这件事)

现链路把"召回"和"判断"两件本质不同的事都做成了"选股":确定性种子池(AlphaSift/Sequoia/screener)已经用策略**挑好并排好了"优势股"**,L1 候选清单实际由它决定;LLM 专家(committee.py)接手时好票已选完,`_merge_capital_evidence` 只能把证据 attach 上去 —— **专家退化为标注者,作用被架空**。更深的缺陷是 `_committee_candidate_score`(committee.py:1847)的"共振加分"奖励"资金+低位同时亮"的票,而干净的低位启动票按定义资金还没进来,**共振范式系统性伤害用户的核心目标(低位买入、后面更易涨)**。

本方案把架构翻转为三段不重叠的漏斗:

```
召回层(策略→特征,只认事实,KPI=召回)
  → 共享事实底表(FactSheet,确定性,每票算一次)
  → 看空红线否决门(硬红线前移:先 veto 再跑 LLM,省成本/不浪费 tool budget)
  → 打法席位(唯一判断层:低位启动 / 动量 / 质量修复,跨维度自洽,有权拒绝/排序)
  → 汇总(冲突打标 + 工具覆盖率 confidence,不打跨席位统一分)
  → regime 分配各席位名额
  → 深入探究(按席位 playbook 把打法压到可执行深度)
  → screening / allocation / adversarial / judge(基本不动)
```

> **与旧讨论稿(`docs/选股链路重构.md`)的关系**:旧稿前半段的"归一化分位 + 富汇总器 score 公式(base+resonance+position+timing+asymmetry−crowding−conflict−risk)"已被本方案**明确废弃**(共振范式系统性伤害低吸)。但其中两点思想被吸收:① 跨源 within-source rank → 降级为 `FeatureFlag.metrics.normalized_rank`(事实,不进全局排序);② 位置/拥挤元数据 → 全部归并进 FactSheet。

设计原则(已与用户对齐):
1. **策略→特征**:召回层只陈述可证伪事实,不排序、不分优劣。
2. **非对称共识**:看空红线全席位共享、确定性否决;看多标准各席位自定,不强求全维度叫好。
3. **按打法切席位,不按数据维度切**;动量席 = 强势延续 + 连板合并;题材/板块作为共享上下文,不独立成席。
4. **跨席位不打统一分**,席位内排序 + 按 `MarketRegime` 分配名额。
5. **打分/阈值常数进 config_registry**,留待历史回放调参,不写死。
6. 下游 screening/allocation/adversarial/judge **输出契约不变**,改动只对候选**加字段**。
7. 红线阈值、各席位名额**留缺口**,由用户后续补(本方案给占位默认值 + TODO 标记)。

参考:`docs/选股链路重构.md`(讨论存档)、`docs/选股池多专家设计.md`(旧愿景,部分作废)。

## 0. 端到端选股链路总览(给读者先看的架构图)

这一节把完整链路按"谁产出什么、传给谁、下游怎么用"讲清楚。后文各章节是工程实现细节。

### 0.1 一句话版本

选股链路不是让 LLM 直接从全市场拍脑袋挑股票,而是先用多来源种子池做**高召回事实采样**,再把每只股票整理成共享 `FactSheet`,交给 3 个"打法席位"独立判断,最后由聚合层按市场状态分配名额,把候选和证据继续传给 `candidate_screening → single_stock_deep_dive → allocation → adversarial → judge`。

### 0.3 种子池怎么构建:17 个来源,先召回再贴标签

种子池入口是 `_build_seed_pool_result(...)`,输出 `SeedItem`。它的目标是"尽量把可能值得看的票召回来",不是在这一层直接决定谁最好。当前 source bucket 如下:

| 类别 | source bucket | 作用 | 典型后续标签 |
|---|---|---|---|
| 本地确定性/价量 | `daily_screener`、`alphasift`、`sequoia`、`low_base_structure` | 从本地日线、形态、低位结构里找价量异常和早期转强 | `pattern` / `position` |
| 资金异动 | `capital_flow_anomaly`、`northbound_stock_connect`、`margin_financing`、`block_trade`、`dragon_tiger` | 捕捉主力资金、北向、融资、大宗、龙虎榜等资金行为 | `capital` |
| 情绪/热度/板块 | `limit_up_pool`、`hot_rank`、`sector_theme` | 捕捉涨停池、热榜和强板块线索 | `limit` / `capital` / `sector` |
| 消息事件 | `event_impact`、`news_momentum` | 捕捉新闻或事件驱动候选 | `news` |
| 基本面/兜底 | `valuation_liquidity`、`fundamental_snapshot`、`fallback` | 捕捉估值流动性、业绩改善、以及兜底样本 | `fundamental` / `unknown` |

构建规则:

- 每个 source 有自己的 `SEED_SOURCE_CAPS`,防止单一来源淹没全池。
- `_passes_hard_exclusion` 先过滤 ST/退市/停牌、流动性过低、交易天数不足等明显不适合样本。
- 单一在线来源失败只写入 `diagnostics/source_quality`,不让整个种子池失败。
- 同一股票被多个来源命中时,后续在 `FeatureRow` 中合并 `recall_sources` 和 `FeatureFlag`,不是重复入池。
- `priority_score` 在旧链路里承担排序作用;新链路里只允许作为 source 内部参考,不再做跨来源统一排名。

### 0.4 从 SeedItem 到 FeatureRow:把"来源"改成"事实标签"

`build_recall_pool(...)` 会把种子池转成席位真正读取的 `FeatureRow`:

```text
SeedItem(code, source, trigger_signals, extras)
  -> FeatureFlag(detector, kind, summary, metrics)
  -> FeatureRow(code, flags[], recall_sources[], fact_sheet)
```

关键语义:

- `FeatureFlag.detector`:说明是哪一个探测器发现了它,例如 `screener:ma_breakout`、`moneyflow_ths`、`low_base:range_low`。
- `FeatureFlag.kind`:把来源归一成事实类型,例如 `pattern/capital/limit/fundamental/position/sector/news`。
- `FeatureFlag.metrics`:只放原始指标或 source 内 rank,不把不同来源的 rank 混成全局分。
- `FeatureRow.fact_sheet`:同一只股票的共享事实底表,三席位看到的是同一份事实。

这样读者可以理解:种子池的职责是"我为什么被系统看见";席位的职责才是"我是否真的值得进入 L1 候选"。

### 0.5 共享 FactSheet:三席位共同读取的事实底表

`FactSheet` 是每只票只计算一次的事实层,主要字段包括:

| 字段组 | 代表字段 | 谁使用 |
|---|---|---|
| 位置/趋势 | `range_pct_60`、`range_pct_120`、`trend_state`、`dist_to_high_20` | 低位启动席、动量席、深挖 playbook |
| 量价状态 | `gain_5d`、`bias_ma20`、`volume_ratio`、`rsi14` | 动量席追高检查、低位席转强确认 |
| 资金状态 | `capital_direction`、`capital_violent_outflow` | 动量席资金真实性、红线否决 |
| 风险/流动性 | `avg_turnover_20`、`liquidity_ok`、`hard_risk_flags` | 红线、聚合、深挖风控 |
| 板块上下文 | `sector_name`、`sector_strength`、`leader_already_up` | 动量席补涨判断、`theme_follow` 深挖 |

重要边界:

- `unknown` 不等于看空。尤其资金 `unknown/neutral` 时,低位启动席仍可判断为 `support/watch`。
- FactSheet Phase A 优先本地日线,不依赖网络;在线资金/板块只作为补充。
- 看空红线属于共享事实层,不属于任何一个席位的"偏好"。

### 0.6 三席位怎么判断:三个完整打法,不是三个数据维度

三席位都读取同一批 `FeatureRow + FactSheet`,但各自按不同打法筛选子集、调用不同工具、输出不同 setup。

| 席位 | 输入偏好 | 核心问题 | 主要工具 | 输出 setup | 典型输出意见 |
|---|---|---|---|---|---|
| `early_turn_desk` 低位启动席 | 低位、形态、价量、资金初步转强 | "是否跌透后刚出现转强,且仍未透支?" | `analyze_price_structure`、`calculate_ma`、`get_volume_analysis`、`analyze_trend`、`get_capital_flow` | `early_turn` | `support`:低位平台放量转强;`watch`:位置低但转强证据不足;`oppose/invalid`:下跌中继或假突破 |
| `momentum_desk` 动量席 | 涨停、资金、强趋势、强板块 | "强势延续是否健康,资金承接是否真实,有没有追高风险?" | `get_capital_flow`、`get_tushare_moneyflow_ths/dc`、`get_tushare_limit_step`、`get_tushare_dragon_tiger_*`、`get_sector_rankings`、`get_volume_analysis` | `trend_continuation` / `capital_momentum` | `support`:趋势健康且有回踩位;`watch`:强但过热需等分歧;`oppose`:高位拥挤/诱多 |
| `quality_repair_desk` 质量修复席 | 基本面、估值、低位/滞涨 | "业绩或景气是否改善,价格是否还没充分反映?" | `get_tushare_daily_basic`、`get_tushare_financial_indicators`、`get_tushare_forecast`、`get_tushare_express`、`analyze_price_structure` | `quality_repair` | `support`:业绩改善且估值未透支;`watch`:改善证据不完整;`oppose`:价值陷阱或已透支 |

席位输出统一用 `ExpertPacketV2`:

```jsonc
{
  "expert": "early_turn_desk",
  "dimension": "early_turn",
  "status": "ok",
  "candidates": [
    {
      "code": "600000",
      "stance": "support",
      "setup_type": "early_turn",
      "reason": "低位平台放量站回关键均线,但需观察回踩不破",
      "evidence": [
        {"tool": "analyze_price_structure", "summary": "..."},
        {"tool": "get_volume_analysis", "summary": "..."}
      ],
      "risks": [
        {"type": "fake_breakout", "summary": "放量失败缩回平台则论点失效"}
      ]
    }
  ],
  "rejected": [
    {"code": "600001", "reason": "位置不低且 RSI 过热"}
  ],
  "diagnostics": []
}
```

席位输出的核心不是"分数",而是:

- `stance`:本席位态度,`support/watch` 才进入聚合候选。
- `setup_type`:告诉深挖后面该按哪套打法继续查。
- `reason`:本席位入池论点。
- `evidence`:本席位实际调用工具得到的证据。
- `risks`:本席位认为论点失效的条件。
- `rejected`:被本席位看过但不认可的样本,用于 Trace 排障。

### 0.7 三席位输出往后传给谁:聚合层先收敛,下游再决策

三席位输出不会直接进入最终报告,中间必须经过 `aggregate_desk_picks(...)` 和 `allocate_slots(...)`:

| 环节 | 输入 | 做什么 | 输出给谁 |
|---|---|---|---|
| `aggregate_desk_picks` | 三个 `ExpertPacketV2` + 原始 `FeatureRow` | 合并同票多席位意见;确定 `primary_desk`;用工具覆盖率算 `confidence`;打 `conflict_flags`;标 `multi_desk_conviction` | `allocate_slots` |
| `allocate_slots` | `AggregatedPool` + `MarketRegime` | 按市场状态给三席位分名额;防守市禁止动量;不足额按规则回填 | `candidate_discovery.candidates` |
| `candidate_screening` | L1 candidates + 证据包 | 初筛每只票是 `deep_dive`、`monitor` 还是 `reject` | 单股深挖/报告 |
| `single_stock_deep_dive` | `setup_type`、`fact_sheet`、席位 evidence、`conflict_flags` | 按打法 playbook 补证据并裁决冲突 | allocation / adversarial / judge |
| `portfolio_allocation` | 深挖结果 | 仓位、入场、止损、组合约束 | adversarial / judge |
| `adversarial_review` | 候选与配置 | 反向审查,找证据缺口和风险 | judge |
| `judge` | 全部上游结论 | 最终裁决,输出可执行建议或等待/拒绝 | 最终报告 |

最终传给下游的候选字段应让读者能反查完整链路:

```jsonc
{
  "code": "600000",
  "name": "示例股票",
  "candidate_source": "thesis_desk_committee",
  "primary_desk": "early_turn_desk",
  "desks": ["early_turn_desk", "quality_repair_desk"],
  "stance": "support",
  "stance_by_desk": {
    "early_turn_desk": "support",
    "quality_repair_desk": "watch"
  },
  "setup_type": "early_turn",
  "reason": "低位启动席入池理由",
  "confidence": 0.75,
  "multi_desk_conviction": true,
  "conflict_flags": [],
  "llm_expert_evidence": {
    "early_turn_desk": [{"tool": "analyze_price_structure", "summary": "..."}],
    "quality_repair_desk": [{"tool": "get_tushare_daily_basic", "summary": "..."}]
  },
  "risks": [{"type": "fake_breakout", "summary": "..."}]
}
```

### 0.8 一个股票从入池到最终报告的例子

```text
600000 被 daily_screener + low_base_structure 召回
  -> FeatureRow.flags = [screener:ma_breakout, low_base:range_low]
  -> FactSheet 显示 range_pct_120=0.28, volume_ratio=1.8, trend_state=neutral
  -> early_turn_desk: support, setup_type=early_turn, 证据=位置/量能/趋势
  -> momentum_desk: watch 或不选,原因=趋势尚未完全走强
  -> quality_repair_desk: 不选,原因=无基本面改善证据
  -> aggregate: primary_desk=early_turn_desk, confidence=工具覆盖率, conflict_flags=[]
  -> allocate: 根据 regime 给低位席名额,进入 L1 candidates
  -> candidate_screening: 判断是否进入 deep_dive
  -> deep_dive: 按 early_turn playbook 检查"低位+转强+失败条件"
  -> judge: 给出等待回踩确认/条件入场/拒绝等最终结论
```

这个例子说明:一只票可以因为"低位启动"进入候选,即使资金还没有强流入;动量席不支持也不等于否决,除非 FactSheet 或后续证据触发明确红线。

## 1. 召回层(特征库)— Layer 0 重写

**定位**:输入全市场,输出"带特征标签 + 廉价指标"的股票清单。只做事实标注、硬排除、去重、粗筛(按特征命中数 / 流动性),**绝不排序、不打优劣分**。

### 1.1 策略降级为特征探测器

把 `_build_seed_pool_result` 内每个 source(daily_screener / capital_flow_anomaly / dragon_tiger / alphasift / sequoia / fundamental_snapshot / low_base / ...)的产物从"候选 + signal_score"改为"**给股票贴 FeatureFlag**"。同一只票被多个探测器命中 → 合并 flags,不再因此"加分"。

新数据结构(放 `schemas.py`):

```python
class FeatureFlag(BaseModel):
    detector: str          # "alphasift:high_tight_flag" / "moneyflow_ths" / "limit_step" ...
    kind: Literal["pattern","capital","limit","fundamental","position","sector","news"]
    summary: str           # 客观事实一句话:"放2.1倍量突破20日高点"
    metrics: Dict[str, Any] = {}   # 该探测器的原始数字(不归一化、不打分)
    as_of: str = "unknown"

class FeatureRow(BaseModel):       # 召回层输出的每只票
    model_config = ConfigDict(extra="allow")
    code: str
    name: str = ""
    market: str = "cn"
    flags: List[FeatureFlag] = []          # 命中的全部特征
    fact_sheet: "FactSheet"                # 见 2.1(确定性事实底表)
    recall_sources: List[str] = []         # 命中了哪些探测器(审计)
    coarse_kept: bool = True               # 粗筛是否保留
    coarse_drop_reason: str = ""
```

**召回源 → FeatureFlag 映射表(P3 落地依据,detector key 命名规范 `{source}:{signal}`):**

| Source | Detector key | kind | 典型 summary 模板 | metrics 关键字段 |
|---|---|---|---|---|
| daily_screener | `screener:ma_breakout` | pattern | "放{vr}倍量突破{n}日高点" | `volume_ratio`,`break_days` |
| capital_flow_anomaly | `moneyflow_ths` / `moneyflow_dc` | capital | "主力净流入{amt},占比{pct}" | `net_inflow`,`net_ratio`,`normalized_rank` |
| dragon_tiger | `dragon_tiger:net_buy` | capital | "龙虎榜机构净买{amt}" | `inst_net`,`seat_type` |
| limit | `limit_step:first_board` / `limit_list` | limit | "首板/{k}连板,封单{amt}" | `limit_times`,`fd_amount`,`open_times` |
| alphasift | `alphasift:high_tight_flag` | pattern | "高位旗形/RPS 前{pct}%" | `rps`,`factor_score`,`normalized_rank` |
| sequoia | `sequoia:volume_breakout` | pattern | "形态分量{score}(降级为事实)" | `pattern_score`,`normalized_rank` |
| low_base | `low_base:range_low` | position | "处 120 日区间{pct}分位" | `range_pct_120`,`gain_5d` |
| fundamental_snapshot | `fundamental:turnaround` | fundamental | "预告/快报盈利改善{yoy}" | `yoy`,`pe_pct` |
| sector | `sector:strong` | sector | "所属板块{name}强度前{pct}%" | `sector_rank_pct` |

> `normalized_rank`(原旧稿 within-source rank)只作为**该 detector 内部事实**留在 metrics 里,**不参与跨源排序**。同一只票被多个探测器命中 → 合并 flags + 合并 recall_sources。

### 1.2 粗筛(可,但不排序)

- **硬排除**(沿用 `_passes_hard_exclusion` + `_local_daily_hard_exclusion_reason`):ST/退市/停牌/流动性下限(`LOCAL_HARD_EXCLUSION_MIN_AVG_TURNOVER`)。
- **粗筛保量**:按"命中特征数 ≥1 且通过硬排除"保留;若总量超过 `RECALL_COARSE_CAP`(默认 120,进 config),按"特征命中数"降序截断 —— 注意这是**命中数**(事实),不是优劣分。命中数相同则保留全部不再细排。
- **"不排序"与 cap 截断的边界澄清**:`RECALL_COARSE_CAP` 是**召回完整性的安全阀,不是优劣排序**。命中数只是"被几个探测器同时注意到"这一客观计数,不代表"更好";它仅用于在极端超量时决定**保谁不保谁**,不决定下游名次(下游名次由席位内 rank + regime 名额定)。理想情况 cap 不触发;一旦触发要记 `selection_recall` 诊断(截断了多少、命中数分布),便于回看 cap 是否设太低误砍。命中数处于截断边界(并列)时**全保**,宁可略超 cap 也不在事实层做优劣裁剪。
- 去重沿用 `_dedupe_by_code`,但合并 flags 而非"先到先得丢弃"。

### 1.3 召回层不再产出 `priority_score` 排序

删除跨源 `priority_score` 比较与 `_compress_seed_priority_score` 的"排序"用途(可保留为某 detector 的内部 metric,但不进全局排序)。**根治"跨源不可比"**:召回层根本不输出全局顺序。

## 2. 共享事实底表 + 看空红线否决门 — "共识"住在这

### 2.1 FactSheet(确定性,每只票算一次,只陈述事实)

新增 `src/agent/candidate_experts_v2/fact_sheet.py`,函数 `build_fact_sheet(code, market, tool_registry, daily_df) -> FactSheet`。优先用召回阶段已加载的本地日线(`get_daily_history`/SQLite)算,避免重复网络调用。

```python
class FactSheet(BaseModel):
    model_config = ConfigDict(extra="allow")
    code: str
    # 资金(确定性,来自 get_capital_flow / moneyflow_ths,缺失填 unknown)
    capital_direction: Literal["inflow","outflow","neutral","unknown"] = "unknown"
    capital_violent_outflow: bool = False        # 红线候选:放量主力夺路出逃
    # 趋势/位置(本地日线算)
    trend_state: Literal["bullish","neutral","bearish","unknown"] = "unknown"
    breakdown_accelerating: bool = False          # 红线候选:有效跌破关键支撑且加速下跌
    range_pct_60: Optional[float] = None          # 60日区间分位 0-1
    range_pct_120: Optional[float] = None
    dist_to_high_20: Optional[float] = None       # 距20日高点 %
    gain_5d: Optional[float] = None               # 近5日涨幅 %
    bias_ma20: Optional[float] = None             # 距MA20乖离 %
    volume_ratio: Optional[float] = None          # 量比
    rsi14: Optional[float] = None
    # 流动性 & 硬风险
    avg_turnover_20: Optional[float] = None
    liquidity_ok: bool = True
    hard_risk_flags: List[str] = []               # st/delist/suspended/litigation/...
    # 板块/题材(共享上下文,替代独立题材席)
    sector_name: str = ""
    sector_strength: Literal["strong","neutral","weak","unknown"] = "unknown"
    sector_rank_pct: Optional[float] = None
    leader_already_up: Optional[bool] = None      # 板块龙头是否已涨(补涨判断用)
    freshness: str = "unknown"
    warnings: List[str] = []
```

`range_pct/bias/rsi/volume_ratio/gain_5d` 复用 `analyze_price_structure`/`calculate_ma`/`get_volume_analysis` 的算法或直接本地计算(旧方案要求的"位置元数据"全部归并到这里,**只算一次**)。

**字段取数优先级与缺失语义(section B):**
- `capital_direction`:优先 `get_capital_flow`(本地/快),缺失退 `get_tushare_moneyflow_ths`,再缺 → `unknown`。
- **`unknown` 不等于看空**:资金 `unknown`/`neutral` 时,低位席**允许 support**(干净低位本就资金未进);只有 `outflow` + 放量(`capital_violent_outflow`)才进红线。这是非对称共识的关键落点。
- `trend_state`/位置类全部用本地日线确定性计算,日线缺失才 `unknown`。
- **freshness / 缓存分桶**:`intraday_bucket` 定义为交易时段每 30 分钟一桶(`09:30-10:00`=b1 … 收盘后=`eod`);FactSheet 缓存 key=`{code}:{date}:{intraday_bucket}`,非交易时段统一落 `eod` 桶。

**两阶段计算(控成本 + 不被网络拖垮):**
- **Phase A(纯本地,无网络)**:对**全部召回 row** 算,只用本地日线(SQLite)+ 已有 seed signals → 位置/趋势/量比/乖离/RSI/流动性/硬风险。这一阶段绝不发网络请求,保证 120 票也秒级完成。
- **Phase B(在线 enrich,按需)**:只对**进入 desk 子集或最终 Top 候选**的票补在线字段(如 `capital_direction` 走 moneyflow、`sector_strength` 走板块接口)。不对全量 120 票发网络请求。
- **网络失败非阻断**:Phase B 任一数据源失败 → 对应字段填 `unknown` 并写入 `warnings` + `source_chain`,**绝不阻断**召回/席位主流程(沿用 `data_provider` fallback 精神)。`capital_direction=unknown` 不杀低位(见上)。

### 2.2 看空红线否决门(确定性,非对称共识的"否决"侧)

新增 `src/agent/candidate_experts_v2/veto_gate.py`:`apply_veto(rows_or_picks) -> (kept, vetoed)`。红线**只看 FactSheet 事实**,与席位无关:

```python
# === RED LINES — 阈值留缺口,用户后续补;先给保守占位默认(进 config_registry) ===
RED_LINES = [
    # ("capital_violent_outflow", True),                # 主力恶性放量出逃
    # ("breakdown_accelerating", True),                  # 破位加速下跌
    # ("liquidity_ok", False),                           # 流动性不足
    # hard_risk_flags 非空(ST/退市/停牌/重大未澄清利空)
]
```

- `hard_risk_flags` 非空 → 直接 veto(这条确定,无需用户定阈值)。
- `capital_violent_outflow` / `breakdown_accelerating` 的**判定阈值留 TODO 占位**(config key 见第 8 节),默认先设为"永不触发"以免误杀,等用户给实战阈值再开启。
- veto 结果是**确定性、可审计**的(记录 vetoed code + reason),不进 LLM。
- **执行位置:前移到席位之前**(`FactSheet → veto → 席位`)。硬红线在 FactSheet 里已确定,先 veto 能省 LLM 成本、避免席位在必死票上浪费 tool budget。因软红线默认不触发,前移阶段实际只拦 `hard_risk_flags`,**不会误杀低位票**;待用户给阈值开启软红线后,误杀风险仍由"永不触发→保守阈值"的渐进开启来控制。

> 非对称核心:红线只做"否决",**绝不存在"必须资金流入/技术看多"这种看多确认门**。低位票资金中性/微弱照样通过,只有"夺路出逃"才被拦。

|---|---|---|---|

### 3.1 席位 = 完整选股逻辑(改造 BaseExpert)

复用现 `experts/base.py` 的 bounded loop / 白名单 / 缓存机制(已成熟),改三点:
1. **输入加 FactSheet**:`run(rows: List[FeatureRow], market, regime)`,每只票把 `fact_sheet` + `flags` 注入 prompt(席位看同一份事实)。
2. **门控语义**:席位输出 `picks`(stance ∈ support/watch)= 进 L1;未被任何席位 pick 的 row → 观察池。
3. **不出 score/confidence**(沿用),只出 stance + evidence + 本席位 setup 标注。confidence 由汇总层用工具覆盖率确定性算。

每个席位:`max_llm_rounds=5, max_tool_calls=10`,只跑在召回层喂进来的 row 上(动量席只看带 limit/capital/pattern flag 的 row;低位席只看 `range_pct_120` 低位的 row;质量席只看带 fundamental flag 的 row → **每席位只吃自己相关的子集,控成本**)。

**desk eligibility 兜底(关键:子集是成本手段,不能变成二次门控):**
子集过滤若太严(例如 `range_pct_120` 因数据缺失为 `None`),低位席可能空跑,反而伤害"资金还没进来的干净低位"。每席位的输入子集按 OR 兜底,例如低位席:

```
early_turn_desk 输入 =
  range_pct_120 <= LOW_BASE_RANGE_PCT_MAX(留缺口,占位默认)
  OR 命中 low_base / sequoia / alphasift 低位类 flag
  OR (未被其他席认领 且 recall 池仍有空位) 时按补充子集纳入,上限 DESK_FALLBACK_SUPPLEMENT_N
```

- 动量席:命中 limit/capital/pattern flag OR `trend_state=bullish` OR 量比/涨幅达标。
- 质量席:命中 fundamental flag OR `daily_basic` 估值分位偏低。
- `range_pct_120=None`(日线不足)**不直接排除**低位席,落入 OR 的第三条补充子集,由席位自行判断。

### 3.4 输出 schema(席位 pick 复用 `ExpertCandidateV2`,但 score/confidence 作废)

**决策:复用 `ExpertCandidateV2`,不新建平行 DeskPick**(符合 CLAUDE.md"不新增平行实现")。但要处理它现有的 `score: float = 50.0` / `confidence: float = 0.5` 默认值(`schemas.py:89`):

- 席位 prompt 已规定**不输出** score/confidence;即便 LLM 误填,**aggregator 一律丢弃**席位 pick 上的 `score`/`confidence`。
- 最终 `confidence` **只由 aggregator 按工具覆盖率计算**(§4.4),写入 `AggregatedCandidate.confidence`;`ExpertCandidateV2.score` 字段在新链路**全程不读取、不向下游传递**(下游排序改由席位内 rank + regime 名额,见 §4.6/§5)。
- 复用枚举:`setup_type`/`setup_subtype`(`CandidateSetupTypeV2`,已含 early_turn/trend_continuation/capital_momentum/quality_repair/theme_follow/unknown)。席位 packet 复用 `ExpertPacketV2`,`dimension` 改填 desk key。
- 验收:加单测断言"席位 pick 即使带 score=99 也不影响最终候选排序与 confidence"。

## 4. 席位汇总:否决门 + 冲突打标 + 席位内排序(不打跨席位统一分)

新增 `aggregate_desk_picks(packets, rows) -> AggregatedPool`,替换 `_committee_candidate_score`/`_sort_committee_candidates`/`_merge_*_evidence` 的"共振加分"逻辑。**三件确定性的事,不做加权融合:**

1. **合并 pick → 候选**:被 ≥1 席位 pick(support/watch)的 row 进 L1;未被 pick 的进观察池(`status=observe`,不进深挖)。
2. **否决门已前移**(见 §2.2):硬红线在席位之前已 veto,此处不再重复;仅当用户后续开启软红线阈值时,可在此做一次"事实复核"二次确认(默认 no-op)。
3. **冲突打标**:pick 的论点与 FactSheet 矛盾 → 打 conflict flag,**不静默保留**,带标记下沉给深挖裁决。冲突类型枚举:

   | conflict flag | 触发条件 | 下沉处理 |
   |---|---|---|
   | `capital_thesis_mismatch` | 动量席标 capital_momentum,但 `capital_direction=outflow` | 深挖 capital_momentum playbook 必须裁决资金真实性 |
   | `thesis_position_mismatch` | 低位席标 early_turn,但 `range_pct_120` 处高位(>阈值) | 深挖 early_turn playbook 复核"是否真低位" |
   | `trend_thesis_mismatch` | 延续/动量论点,但 `trend_state=bearish` | 深挖复核趋势结构 |
   | `quality_price_mismatch` | 质量席标 quality_repair,但价格已大涨(估值透支信号) | 深挖复核"价格滞后"是否成立 |

4. **confidence(确定性,落地"工具覆盖率替换 LLM confidence")**:
   `confidence = 已被工具 evidence 覆盖的关键维度数 / 本席位期望维度数`。**dimension ↔ tool 映射**(放 manifest 或 config,每席一张):

   | desk | expected_dims | dimension ← tool |
   |---|---|---|
   | early_turn_desk | position, volume, trend, capital | position ← analyze_price_structure/calculate_ma;volume ← get_volume_analysis;trend ← analyze_trend;capital ← get_capital_flow |
   | momentum_desk | trend, volume, capital, structure | trend ← analyze_trend;capital ← moneyflow_ths/dc;structure ← limit_step/dragon_tiger;volume ← get_volume_analysis |
   | quality_repair_desk | earnings, valuation, position | earnings ← financial_indicators/forecast/express;valuation ← daily_basic;position ← analyze_price_structure |

   - 同一维度多工具命中**只计 1 次覆盖**(分子是"被覆盖的维度数",不是工具数)。
   - 工具返回 `unknown`/数据不足 **不算覆盖**(但 capital 维度 `unknown` 不视为席位失败,见 §2.1)。
5. **多席位同选同一票(方向一致)** = 真共识 → 标 `multi_desk_conviction=True`,**提高深挖优先级**(注意:这与旧"共振加分"不同,是两套独立打法不约而同,不是一票六维都亮)。
   - **primary_desk 归属**(allocate 名额计入哪个席位):取 stance 更强者(support>watch),并列取 confidence 更高者,再并列按 config 的席位优先序(默认 `early_turn > quality_repair > momentum`,体现低吸优先)。`setup_type` 以 primary_desk 的标注为准。一张选票只占一个席位名额,避免重复计数。
6. **席位内排序**:每席位内部按 `(multi_desk_conviction, confidence, 关键 metric)` 排序,各交 Top N(N 进 config,默认 5);**不产出跨席位全局分**。allocate 时即以各席位的这份内部排序为准取名额。

`AggregatedPool` 结构:
```python
class AggregatedCandidate(BaseModel):
    model_config = ConfigDict(extra="allow")
    code: str; name: str = ""; market: str = "cn"
    setup_type: CandidateSetupTypeV2
    desks: List[str] = []                  # 哪些席位选了它
    stance_by_desk: Dict[str,str] = {}
    confidence: float = 0.5                # 工具覆盖率算出
    multi_desk_conviction: bool = False
    conflict_flags: List[str] = []
    fact_sheet: FactSheet
    evidence_by_desk: Dict[str, List[EvidenceItem]] = {}
    risks: List[RiskNote] = []
    observe_only: bool = False

class AggregatedPool(BaseModel):
    by_desk: Dict[str, List[AggregatedCandidate]] = {}   # 席位内已排序
    vetoed: List[Dict[str,Any]] = []
    observe: List[AggregatedCandidate] = []
    regime: str = "unknown"
    diagnostics: List[Dict[str,Any]] = []
```

### 7.0 本层目标:把"选股深挖"从通用个股分析 prompt 里拆出来

当前需要补齐的最后一层不是再做一次"全市场选股",也不是复用 `planning_prompts.py` 里的账户通用分析,而是专门处理**三席位已经选出来的 L1 候选**:

```text
三席位候选入池榜 candidates
  -> candidate_screening 初筛
  -> selection_deep_dive_targets 选择 1-3 只
  -> 选股专用 single_stock_deep_dive prompt
  -> deep_dive_results.json
  -> 最终报告逐股深挖段 + allocation/adversarial/judge
```

拆分原则:

- `planning_prompts.py` 只保留规划 Agent / 通用账户任务的系统规则,不再承载选股深挖细节。
- `stock_selection_prompts.py` 或后续独立的 `stock_selection_deep_dive_prompts.py` 承载选股流水线专用 prompt。
- `position_review` / `entry_analysis` 的单票分析可以有自己的 prompt,但不得和 `watchlist_scan` 的候选深挖共用一套长 prompt。
- 选股深挖只分析**已经被三席位和初筛放行的候选**,不新增候选、不替换股票、不做最终组合仓位。

推荐文件边界:

```text
src/agent/planning_prompts.py
  # 只管任务识别、规划、账户通用行为边界

src/agent/stock_selection_prompts.py
  # 保留 candidate_discovery / candidate_screening / allocation / adversarial / judge
  # 可继续导出 build_deep_dive_prompt 作为兼容入口

src/agent/stock_selection_deep_dive_prompts.py

  # build_selection_deep_dive_prompt(payload)
  # build_selection_deep_dive_batch_summary_prompt(payload)  # 可选,只做汇总不做逐股裁决

src/agent/entry_analysis_prompts.py        # 后续可拆:用户指定单股能不能买
```

> 关键边界:选股深挖 prompt 的上游输入是 `primary_desk/setup_type/fact_sheet/llm_expert_evidence/conflict_flags/screening_result`,而通用个股分析 prompt 的上游输入通常是用户指定股票 + 账户/持仓问题。两者的目标不同,不要长期混在一条 prompt 里。

### 7.1.1 深挖目标选择:最多 3 只,最少 1 只

本层的目标不是覆盖所有 L1 候选,而是把报告时间花在最值得解释的 1-3 只上。

**硬规则:**

- `SELECTION_DEEP_DIVE_MIN=1`:只要候选发现和初筛没有全失败,最终至少深挖 1 只,否则报告只能给"本轮无可深挖候选"。
- `SELECTION_DEEP_DIVE_MAX=3`:最多深挖 3 只,避免整轮选股被单股长分析拖慢。
- 初筛明确 `reject` 的候选不得因为补足 1 只而进入深挖;如果全被 reject,深挖结果为空,报告明确说明"三席位候选全部被初筛淘汰"。
- `pool_fallback` 可以用于补足最少 1 只或丰富报告,但必须标记 provenance,不能伪装成已通过初筛。

推荐选择顺序:

1. `candidate_screening.full.shortlist` 中 `screening_result=deep_dive` 的候选,按初筛分/候选池顺序取。
2. 若不足 1-3 只,补 `screening_result=monitor` 但未被 reject 的候选。
3. 若仍不足最少 1 只,按 `candidate_discovery.candidates` 的席位名额顺序补 `pool_fallback`。
4. 同一股票只深挖一次;多席位共选只作为 `multi_desk_conviction` 提升优先级,不重复占名额。

排序权重建议:

```text
deep_dive_priority =
  screening_result(deep_dive > monitor > pool_fallback)
  + primary_desk quota order
  + multi_desk_conviction
  + confidence(tool coverage)
  - conflict_penalty(有冲突但未裁决)
  - provenance_penalty(pool_fallback)
```

### 7.1.2 调用方式:默认 3 次 1 只,不建议 1 次塞 3 只

推荐默认执行方式是**每只股票独立一次深挖 prompt**,最多 3 次:

```text
for code in deep_dive_targets[:3]:
    evidence = reuse_balanced_evidence_or_collect(code)
    prompt = build_selection_deep_dive_prompt(one_candidate_payload)
    result = call_llm(stage_name=f"single_stock_deep_dive:{code}")
combine_deep_dive_outputs(results)
```

原因:

- 三只股票可能来自不同 `setup_type`(低位启动/动量/质量修复),单个 prompt 更容易走对 playbook。
- 单股 JSON schema 更稳定,不会出现模型把 A 股证据写到 B 股上的串票问题。
- 单只失败、超时或数据缺口可以单独降级,不会污染另外两只。
- 报告天然需要逐股小节;单股 artifact 也方便 Trace 展开。

效率控制不靠"把 3 只塞进一个 prompt",而靠:

- 深挖上限固定为 3。
- 优先复用 `balanced_candidate_evidence`、`FactSheet` 和席位 evidence,只补缺口。
- 每只 deep dive 设置独立 timeout,失败只降级该股票。
- 证据收集可并行;LLM 调用可保守串行,若后续成本可控再改为最多 2-3 并发。

`1 次 3 只`只作为可选 batch 模式,适用条件很窄:

- 不允许模型再调用工具,所有逐股证据都已收集完毕。
- 三只股票 `setup_type` 相同或高度相近。
- 只做**报告摘要压缩**,不做逐股裁决。

因此当前设计建议:

```text
默认: 3 x single-stock prompt
可选: 1 x batch summary prompt(只汇总已完成的 1-3 份 deep_dive_results)
```

### 7.1.5 选股专用深挖 prompt 骨架

```text
你是"选股候选深挖 Agent",只负责三席位候选的逐股复核。
你不是 planning Agent,不是持仓诊断 Agent,也不是最终 Judge。

任务:
基于三席位给出的原始论点、FactSheet、初筛结果和已收集 EvidenceCard,
判断这只股票是否仍值得进入最终组合配置。

边界:
- 不新增股票,不替换股票,不扩大到全市场。
- 不把 L1 入池分当成买入分。
- 不重复拉取已有证据,只补缺口或裁决冲突。
- 如果 provenance=pool_fallback,最高只能给 conditional_pass/monitor,除非证据极完整且无主要反证。

必须完成:
1. 复核 primary_desk 的原始 thesis 是否成立。
2. 按 setup_type 选择 playbook,不要泛泛六维打分。
3. 裁决 conflict_flags。
4. 输出能直接写进报告的 report_headline/report_summary。
5. 同时给 stop_loss 和 failure_condition,并说明二者区别。
6. 给 no_chase_line,防止报告包装成追高建议。
7. 明确 missing_evidence 和工具失败如何影响结论强度。

输出:
严格 JSON,符合 selection_single_stock_deep_dive schema。
```

### 7.1.6 五类 playbook 与三席位关系

三席位传来的 `setup_type` 决定深挖 playbook:

| primary_desk | setup_type | 深挖核心 | 报告重点 |
|---|---|---|---|
| `early_turn_desk` | `early_turn` | 低位是否真低、转强是否成立、是否不是下跌中继 | "低位启动条件"、回踩确认、失效平台 |
| `momentum_desk` | `trend_continuation` | 趋势是否健康、是否过热、是否有舒服回踩位 | "强势延续但不追高"、回踩位、禁追线 |
| `momentum_desk` | `capital_momentum` | 资金承接是否真实、连板/龙虎是否诱多 | "资金接力质量"、分歧转一致、破板风险 |
| `quality_repair_desk` | `quality_repair` | 基本面改善是否真实、估值是否透支、价格是否滞后 | "质量修复逻辑"、业绩证伪条件 |
| 任意席位 | `theme_follow` | 板块强度是否传导到个股,是否只是纯跟风 | "补涨有效性"、板块退潮风险 |

`unknown` 只作为保守兜底。长期目标是三席位候选都必须带 `setup_type`;否则 Trace 需要标记为 `setup_type_missing`。


### 7.2 五套 playbook(判定内核,内嵌进 prompt)

| setup | 核心论点(必须证伪) | 必查证据 | 入场 | 止损(价格) | failure_condition(论点证伪,可非价格) |
|---|---|---|---|---|---|
| early_turn | 拐点成立且未透支 | 低位+首次转强+资金由负转正 | 回踩不破平台/放量确认 | 平台下沿/启动低点 | 资金回流仅一天、放量失败缩回、跌回平台 |
| trend_continuation | 趋势健康、有回踩位、未追高 | 趋势结构+均线多头+乖离/RSI检查+回踩位 | 回踩MA/突破回踩 | 突破位/趋势线 | 量价透支、次日大幅分歧、趋势破坏 |
| capital_momentum | 资金承接真实非诱多 | 主力净流入持续性+龙虎结构+封板强度+连板高度 | 竞价/分歧转一致 | 破封板成本/首板低点 | 开板、诱多、资金次日撤离 |
| quality_repair | 业绩/景气改善且估值未透支、价格滞后 | 盈利质量/亏损收窄+估值位置+景气+价格滞后 | 偏价值、容忍慢 | 基本面逻辑破坏 | 业绩证伪、估值已透支、景气逆转 |
| theme_follow | 板块强且个股为有效补涨 | 板块强度+龙头已涨/二线未涨+资金流向二线 | 板块回踩企稳 | 板块走弱 | 纯跟风、板块见顶 |

### 7.3 顺手修的 3 个老问题
- **failure_condition vs stop_loss 解耦**:每 playbook 明确二者定义(failure=论点证伪、可非价格;stop_loss=价格风控),prompt 要求两者都给并解释差异。
- **证据复用**:REUSED_EVIDENCE_BLOCK 注入 fact_sheet + 席位 evidence,指令"已有数据的维度只补缺口/过期项,不重复全量取证"。
- **市场逻辑剥离**:涨停/龙虎/北向进 `MARKET_BLOCK[cn]`,港美各自 block。

**解析与空值语义(必须在 config_registry 明确)**:

### 8.3 性能 / 并发 / 降级
- 召回 + FactSheet 全确定性,**本地 SQLite 优先**,FactSheet 每票只算一次(下游全程复用)。
- 3 席位并行(复用 `run_experts_parallel`),每席位只吃自己子集；席位内部按单只 seed/FeatureRow 顺序调用 LLM,不会把 20 只股票一次性塞进同一个 prompt。每次 LLM 工具调用显式使用 `AGENT_CANDIDATE_EXPERT_TIMEOUT_SECONDS`(默认 60s),避免继承 LiteLLM 长超时导致席位结果晚到；外层 seed wall-clock guard 按「首轮 LLM + 工具执行 + 二轮/三轮 LLM」留出完整余量,避免先于 LLM 硬超时误杀。

**成本预算量化上限(section,防失控):**
- 最坏情况:`RECALL_COARSE_CAP=120` 票 × 3 席位,若每票都跑 LLM 不可接受。靠三道闸控制:① veto 前移先砍硬红线;② 每席位只吃自己子集(典型每席 ≤ 30-40 票);③ 每席位 `max_tool_calls=10` 是**整席预算**,不是每票预算 —— 席位需在 prompt 里被告知"优先核实最像本打法的 3-6 只,而非全量"。
- 量化红线:单次 discovery 总 LLM 调用 `≤ 3 席 × max_llm_rounds(5)`,总 tool 调用 `≤ 3 席 × 10 = 30`;超限直接截断并记 diagnostics。
- FactSheet 工具调用走确定性本地优先,不计入席位 tool 预算。

**失败契约(三席位是候选闸门,不做 seed fallback):**
- 某席位超时/报错 → 跳过,其余继续。
- **全部席位失败或 thesis desk 空输出 → 本轮候选发现失败**,`candidate_discovery.status=failed`,`candidate_discovery.candidates=[]`,`llm_expert_committee.fallback=false`。
  - seed pool 只保留为输入 provenance 和排障诊断,不得自动提升为 L1 候选。
  - stock_selection 主流程在候选发现阶段 fail-fast,不继续 screening/deep_dive/allocation,避免把未通过席位判断的 seed 包装成可深挖候选。
  - Trace 必须保留 `seed_pool_summary`、`thesis_desk_packets`、`thesis_desk_packets[].per_seed_packets`、`thesis_desk_diagnostics`,前端据此展示每个席位、每只 seed 的真实输出/超时原因。
- 缓存:沿用 `cache.py` `seed_hash`,key 改 `{desk}:{market}:{date}:{rows_hash}`;FactSheet 按 `{code}:{date}:{intraday_bucket}` 缓存(分桶定义见 §2.1)。

- **低位席候选占比**:`early_turn` setup 候选在 L1 中占比达到预期区间(对照旧模式应**显著上升**,印证低吸保护生效)。

- **degraded 比例**:`selection_desk_degraded=true` 占比 ≤ 阈值(如 <5%),否则说明席位稳定性不足,不切默认。
- **性能**:平均 discovery 耗时、总工具调用数在预算内(LLM ≤3×5、tool ≤30,见 §8.3)。
- **新旧候选重合率 + 差异样例**:抽样核对新模式剔除/新增的票是否符合"低吸优先、不追高"预期。
- **稳定性**:至少 N 次(如 ≥20)连续 trace **无 schema/JSON 解析失败**。

任一项不达标 → 保持 opt-in,不改默认。
