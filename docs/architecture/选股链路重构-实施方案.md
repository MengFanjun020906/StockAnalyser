# 选股链路重构 · 详细实施方案(召回 / 席位 / 深入探究)

## Context(为什么做这件事)

现链路把"召回"和"判断"两件本质不同的事都做成了"选股":确定性种子池(AlphaSift/Sequoia/screener)已经用策略**挑好并排好了"优势股"**,L1 候选清单实际由它决定;LLM 专家(committee.py)接手时好票已选完,`_merge_capital_evidence` 只能把证据 attach 上去 —— **专家退化为标注者,作用被架空**。更深的缺陷是 `_committee_candidate_score`(committee.py:1847)的"共振加分"奖励"资金+低位同时亮"的票,而干净的低位启动票按定义资金还没进来,**共振范式系统性伤害用户的核心目标(低位买入、后面更易涨)**。

本方案把架构翻转为三段不重叠的漏斗:

```
召回层(策略→特征,只认事实,KPI=召回)
  → 共享事实底表(FactSheet,确定性,每票算一次)
  → SeedFactPacket(并行在线取数,固定 JSON 模板,每票取一次)
  → 看空红线否决门(硬红线前移:先 veto 再跑 LLM,省成本/不浪费 tool budget)
  → 打法席位(唯一判断层:优先读取 SeedFactPacket,只做少量补证工具)
  → 汇总(冲突打标 + 工具覆盖率 confidence,不打跨席位统一分)
  → regime 分配各席位名额
  → 深入探究(按席位 playbook 把打法压到可执行深度)
  → Meta-Agent/Orchestrator(资产定性 + 场景与约束包,不算买卖点)
  → 点位计算层(内部 stage key: `pricing_agent`,按硬约束计算 If-Then 条件单)
  → 组合规划 → 反方审查 → Judge → final.md(最终风控与报告渲染)
```

> **与旧讨论稿(`docs/plans/选股链路重构.md`)的关系**:旧稿前半段的"归一化分位 + 富汇总器 score 公式(base+resonance+position+timing+asymmetry−crowding−conflict−risk)"已被本方案**明确废弃**(共振范式系统性伤害低吸)。但其中两点思想被吸收:① 跨源 within-source rank → 降级为 `FeatureFlag.metrics.normalized_rank`(事实,不进全局排序);② 位置/拥挤元数据 → 全部归并进 FactSheet。

设计原则(已与用户对齐):
1. **策略→特征**:召回层只陈述可证伪事实,不排序、不分优劣。
2. **非对称共识**:看空红线全席位共享、确定性否决;看多标准各席位自定,不强求全维度叫好。
3. **按打法切席位,不按数据维度切**;动量席 = 强势延续 + 连板合并;题材/板块作为共享上下文,不独立成席。
4. **跨席位不打统一分**,席位内排序 + 按 `MarketRegime` 分配名额。
5. **打分/阈值常数进 config_registry**,留待历史回放调参,不写死。
6. 下游 screening/allocation/adversarial/judge **输出契约不变**,改动只对候选**加字段**。
7. 红线阈值、各席位名额**留缺口**,由用户后续补(本方案给占位默认值 + TODO 标记)。

参考:`docs/plans/选股链路重构.md`(讨论存档)、`docs/plans/选股池多专家设计.md`(旧愿景,部分作废)。

## 0. 端到端选股链路总览(给读者先看的架构图)

这一节把完整链路按"谁产出什么、传给谁、下游怎么用"讲清楚。后文各章节是工程实现细节。

### 0.1 一句话版本

选股链路不是让 LLM 直接从全市场拍脑袋挑股票,而是先用多来源种子池做**高召回事实采样**,再把每只股票整理成共享 `FactSheet + SeedFactPacket`。`SeedFactPacket` 在进入席位前并行取好大部分通用数据,3 个"打法席位"优先读取同一份 JSON 事实模板,只在关键缺口上补少量工具。最后由聚合层按市场状态分配名额,把候选和证据继续传给 `candidate_screening → single_stock_deep_dive → Meta-Agent 场景约束 → 点位计算条件单 → 组合规划 → 反方审查 → Judge → final.md`。

### 0.3 种子池怎么构建:主来源先召回再贴标签

种子池入口是 `_build_seed_pool_result(...)`,输出 `SeedItem`。它的目标是"尽量把可能值得看的票召回来",不是在这一层直接决定谁最好。当前 source bucket 如下:

| 类别 | source bucket | 作用 | 典型后续标签 |
|---|---|---|---|
| 本地确定性/价量 | `daily_screener`、`alphasift`、`sequoia` | 从本地日线、AlphaSift 多因子和 Sequoia 技术形态里找价量异常、突破和趋势延续 | `pattern` / `position` |
| 资金异动 | `capital_flow_anomaly`、`margin_financing`、`block_trade`、`dragon_tiger` | 捕捉主力资金、融资、大宗、龙虎榜等资金行为 | `capital` |
| 情绪/热度/板块 | `limit_up_pool`、`hot_rank`、`sector_theme` | 捕捉涨停池、热榜和强板块线索 | `limit` / `capital` / `sector` |
| 消息事件 | `news_theme_daily` | 捕捉盘前日报主题和原文高质量消息主题 | `news` |
| 基本面/兜底 | `valuation_liquidity`、`fallback` | 捕捉估值流动性、以及兜底样本 | `fundamental` / `unknown` |

构建规则:

- 每个 source 有自己的 `SEED_SOURCE_CAPS`,防止单一来源淹没全池。
- `_passes_hard_exclusion` 先过滤 ST/退市/停牌、流动性过低、交易天数不足等明显不适合样本。
- 单一在线来源失败只写入 `diagnostics/source_quality`,不让整个种子池失败。
- 同一股票被多个来源命中时,后续在 `FeatureRow` 中合并 `recall_sources` 和 `FeatureFlag`,不是重复入池。
- `priority_score` 在旧链路里承担排序作用;新链路里只允许作为 source 内部诊断参考,不再做跨来源统一排名。对外的 seed pool preview 和候选 payload 不输出顶层 `priority_score/signal_score/score`;如需排障,只放在 `source_diagnostics` 或 `metrics.source_diagnostics`。
- 最终 seed pool 合并按加权 source quota 分配:`user_watchlist` 保持最高优先级,AlphaSift/Sequoia 作为主干来源使用更高 cap 和权重;某个来源样本不足或与已入池股票重复时,未用名额再分配给其它可用来源。禁止因为单一前置来源先填满 `AGENT_SEED_POOL_TOTAL_LIMIT` 而让资金、涨停、龙虎榜、AlphaSift/Sequoia 等后续 source 全部消失;这些 source 若返回 `ok/count>0`,即使最终因去重或 total limit 未入池,Trace 也必须能从 diagnostics 看出原因。
- `low_base_structure` 当前不进入默认 seed pool 主链路:实际胜率/质量不及 AlphaSift 和 Sequoia,默认构建不再调用 `_build_low_base_structure_seeds`;低位相关判断只保留在后续席位标签和个股深挖中作为辅助事实。
- `northbound_stock_connect` 当前不进入主 seed pool:`hsgt_top10` 在当前 Tushare 权限下不可用,避免一个长期失败 source 占用诊断噪音和 quota 预期。
- `hot_rank` 当前不再调用 Tushare `ths_hot`,改用 StockAPI `/v1/change/renQi` 股票人气榜补关注度 seed。
- `sector_theme` 优先接入 StockAPI `/v1/hotBkJlrDr` 热点板块和 `/v1/hotBkJlrLongTou` 热点板块龙头股;前者提供板块净额、资金净流入天数、强度,后者直接生成板块龙头 seed。
- `news_theme_daily` 接入东方财富财经早餐 `ak.stock_info_cjzc_em()`,按 `trade_date` 锚定 6 点盘前日报:当天 06:00 前运行时取上一自然日财经早餐,06:00 及以后取当日财经早餐;历史回放传入非当天日期时保持精确匹配。它用"结构化正则 + 本地概念字典 + 可选 jieba 分词 + 规则引擎"抽取盘前主题和公司新闻诊断。它不因公司名/股票代码被点名就直接产 seed;真正产码走本地概念/板块映射与风险词过滤。它是盘前主题 source,不是收盘后新闻;2026-06-02 收盘后复跑仍取 2026-06-02 早上 6 点那篇财经早餐。
- `news_theme_daily` 的 source cap 从 6 提高到 8,消息池可多给 2 个候选,用于承接高质量原文主题如存储、光模块、光连接、AI 服务器材料等。
- `event_impact`、`news_momentum`、`fundamental_snapshot` 当前不进入四席位主 seed pool:这三类历史 precision 不稳定,容易把低质量消息异动或弱基本面样本挤进池。它们后续可作为深层诊断、个股补证或前端观察项保留,但不作为 `_build_seed_pool_result` 主召回来源。
- `discover_watchlist_candidates_auto` 在线补充入口只允许 `sector_theme/alphasift/sequoia` 等高质量 bucket 回灌;`event_impact/news_momentum` 不再拆成独立 seed bucket。

### 0.4 从 SeedItem 到 FeatureRow:把"来源"改成"事实标签"

`build_recall_pool(...)` 会把种子池转成席位真正读取的 `FeatureRow`:

```text
SeedItem(code, source, trigger_signals, extras)
  -> FeatureFlag(detector, kind, summary, metrics)
  -> FeatureRow(code, flags[], recall_sources[], fact_sheet)
```

关键语义:

- `FeatureFlag.detector`:说明是哪一个探测器发现了它,例如 `screener:ma_breakout`、`moneyflow_dc`、`low_base:range_low`。
- `FeatureFlag.kind`:把来源归一成事实类型,例如 `pattern/capital/limit/fundamental/position/sector/news`。
- `FeatureFlag.metrics`:只放原始指标或 source 内 rank,不把不同来源的 rank 混成全局分。
- `FeatureRow.fact_sheet`:同一只股票的共享事实底表,四席位看到的是同一份事实。

这样读者可以理解:种子池的职责是"我为什么被系统看见";席位的职责才是"我是否真的值得进入 L1 候选"。

### 0.4.1 `news_theme_daily`:盘前日报主题 source

`news_theme_daily` 专门解决"早上 6 点财经早餐已经提示主题,但盘中异动源还没形成个股事件"的问题。它的输入必须分两段:先用东方财富财经早餐列表接口定位当天文章,再读取文章原文做主题抽取。列表接口的 `摘要` 只能作为文章缺失时的降级输入,不能替代原文。

```python
import akshare as ak

df = ak.stock_info_cjzc_em()
```

原文读取规则:

- `stock_info_cjzc_em()` 只用于拿 `标题/摘要/发布时间/链接`,其中 `摘要` 往往只包含前三条新闻,不能覆盖"每日精选/热点题材/公司新闻"全文。
- 工具拿到 `链接` 后必须抓取东财文章原文,解析 `ContentBody`,并按 `<h3>` 分区形成 `article_sections`,典型 section 包括 `每日精选`、`热点题材`、`公司新闻`。
- 主题抽取优先读 `每日精选/热点题材` 原文 section;`公司新闻` 只用于 `company_events` 诊断和风险过滤,默认不产 seed。
- 若原文抓取失败,工具可降级到 `标题 + 摘要`,但必须在输出中标记 `article_fetch_status=failed|empty|missing` 和错误信息,Trace 不得让用户误以为已经读过全文。

交易日归属规则:

- 工具不按"最新一篇"粗暴取；seed pool 调用时 `news_theme_daily` 优先使用本次运行日/传入 `today`,而不是 Tushare 最近可用交易日,避免收盘后 Tushare 仍停在上一交易日时漏掉当天 6 点日报。
- 目标日期路由分为 `requested_target_date` 和实际匹配的 `target_date`:当请求日期是系统当天且当前本地时间早于 06:00 时,`target_date` 自动解析为上一自然日,并标记 `target_date_rule=pre_6_use_previous_daily`;06:00 及以后 `target_date` 等于当天,标记 `post_6_use_today_daily`;历史回放非当天日期标记 `historical_replay_exact`。
- 当天 6 点财经早餐属于同一天的 `pre_market_daily`;收盘后、晚上或回放同一交易日时,仍取该交易日早上 6 点的日报。
- 历史回放传入非当天日期时保持精确匹配,工具层不再按当前时间做自然日漂移;只有显式允许 `allow_previous=true` 且实际 `target_date` 缺失时,才可取最近上一日文章,并标记 `stale_previous_daily`。
- Trace 必须暴露 `requested_target_date`、`target_date`、`target_date_rule`、`matched_publish_date`,让用户能看到"请求的是哪天"和"实际读的是哪篇日报"。

产码规则:

| 路径 | 是否产股票代码 | 置信度 | 说明 |
|---|---:|---|---|
| 日报直接点名股票/公司 | 默认否 | `diagnostic` | 公司新闻只做事件定性/避雷诊断;即使点名公司,也不直接产 seed,防止澄清、否认、减持、亏损等负面新闻误入池 |
| 日报点名主题/板块,命中本地概念字典 | 是 | `medium-high` | 例如 `MLCC -> 被动元件/电子元件 -> 三环集团/风华高科/洁美科技` |
| 日报主题与已有 seed 的 `business_context` 匹配 | 是/增强原 seed | `medium-high` | 已经由 `sequoia/alphasift/hot_rank` 召回的股票,若业务上下文命中日报主题,追加 `news_theme_daily` evidence |
| 只有泛主题,无法可靠映射个股 | 否 | `low` | 只落 `theme_trace`,不硬塞弱相关股票 |

输出 seed 必须保留证据:

```jsonc
{
  "source": "news_theme_daily",
  "theme": "MLCC",
  "polarity": "positive",
  "directness": "concept_board | overlap_existing_seed",
  "evidence_section": "每日精选",
  "matched_keywords": ["MLCC", "AI服务器", "供给瓶颈"],
  "related_boards": ["电子元件", "被动元件"],
  "source_url": "https://finance.eastmoney.com/a/...",
  "confidence": "high"
}
```

硬边界:

- `news_theme_daily` 不使用 LLM 做全市场主题召回;主题和股票映射必须来自确定性标题/摘要/正文解析、本地概念字典、板块映射或已有 seed 交叉。
- 只读 `stock_info_cjzc_em().摘要` 不算闭环。摘要命中的主题可以作为降级结果,但完整链路必须读取原文正文并落盘 `article_sections`、`article_fetch_status`、`theme_score`、`evidence_section`。
- `英伟达/NVIDIA/黄仁勋/Jensen Huang/CUDA/GB200/Blackwell` 等词属于高影响产业催化词,只在 `每日精选/热点题材` 主题证据段内提升 `theme_score`,用于把更接近 AI 算力核心链条的主题前置;它不能让 `公司新闻` 直接产 seed,也不能覆盖"不属实/未开展/澄清"等否认词的一票否决。
- 被点名公司不等于利好。若正文出现"澄清/否认/减持/风险提示/亏损/监管"等负向词,只能进入 `company_events` 诊断,不得作为 positive seed。
- 辟谣/澄清词一票否决。命中"不涉及/未开展/不属实/澄清/无规模化/未参与"等词时,即使同段出现热门概念,该公司事件也只能标记为 `deny_or_clarification`。
- 单日 cap 默认 `8`,每个主题最多 `1-2` 只,防止盘前日报淹没整个 seed pool,同时给消息池多 2 个候选名额承接更完整的原文主题。

### 0.5 共享 FactSheet:四席位共同读取的事实底表

`FactSheet` 是每只票只计算一次的事实层,主要字段包括:

| 字段组 | 代表字段 | 谁使用 |
|---|---|---|
| 位置/趋势 | `range_pct_60`、`range_pct_120`、`trend_state`、`dist_to_high_20` | 低位启动席、动量席、深挖 playbook |
| 量价状态 | `gain_5d`、`bias_ma20`、`volume_ratio`、`rsi14` | 动量席追高检查、低位席转强确认 |
| 资金状态 | `capital_direction`、`capital_violent_outflow` | 动量席资金真实性、红线否决 |
| 风险/流动性 | `avg_turnover_20`、`liquidity_ok`、`hard_risk_flags` | 红线、聚合、深挖风控 |
| 板块上下文 | `sector_name`、`sector_strength`、`leader_already_up` | 动量席补涨判断、`theme_follow` 深挖 |

重要边界:

- `unknown` 不等于看空。尤其资金 `unknown/neutral` 时,低位启动席仍可判断为 `support/watch`。
- FactSheet Phase A 优先本地日线,不依赖网络;在线资金/板块只作为补充。
- 看空红线属于共享事实层,不属于任何一个席位的"偏好"。

### 0.5.1 SeedFactPacket:席位前统一并行取数的固定 JSON 模板

`FactSheet` 只放确定性、轻量、可复用的底表字段;但真实席位判断还需要趋势结构、均线、量能、资金、基本面、板块、主题催化等较重工具结果。为了避免"20 个 seed × 4 个席位 × 重复工具"的成本爆炸,在进入四席位前新增 `SeedFactPacket`:

```text
FeatureRow + FactSheet
  -> build_seed_fact_packets_parallel(rows)
  -> FeatureRow.seed_fact
  -> 四席位共享读取同一份 seed_fact JSON
```

固定模板:

```jsonc
{
  "code": "600027",
  "name": "华电国际",
  "market": "cn",
  "recall_sources": ["daily_screener"],
  "flags": [{"detector": "screener:ma_breakout", "summary": "..."}],
  "fact_sheet": {"range_pct_120": 0.91, "trend_state": "bullish"},
  "business_context": {
    "status": "partial",
    "broad_industries": ["电力能源"],
    "board_names": [{"name": "火电", "source": "get_stock_business_context"}],
    "theme_clues": [{"source": "feature_flag", "evidence": "火电板块资金净流入"}],
    "confidence": "medium"
  },
  "facts": {
    "analyze_price_structure": {"status": "ok", "data": {}},
    "analyze_trend": {"status": "ok", "data": {}},
    "calculate_ma": {"status": "ok", "data": {}},
    "get_volume_analysis": {"status": "ok", "data": {}},
    "get_capital_flow": {"status": "ok", "data": {}},
    "get_stock_business_context": {"status": "ok", "data": {}, "errors": []}
  },
  "data_quality": {
    "status": "partial",
    "tool_count": 6,
    "ok_tools": 5,
    "failed_tools": [],
    "missing_tools": [],
    "elapsed_ms": 8120
  }
}
```

执行规则:

- **真正并行**:按 `(seed, tool)` 维度提交线程池任务,不是席位内串行慢慢取。默认取数 worker 数按配置上限控制,避免压垮数据源。
- **主分析工具批次也必须真并行**:`planning_execute` 首轮可能同时请求 10+ 个工具,runner 不得用过小 worker 池让后续工具在队列里等待后又被同一个 `AGENT_TOOL_CALL_TIMEOUT_SECONDS` 批次超时误判。正常工具批次应按请求宽度启动,并用上限防止异常工具洪泛。
- **每只 seed 只取一次**:四席位看到同一份 `SeedFactPacket`;同一个 `get_stock_business_context` 不应被低位席、动量席、质量席、主题催化席重复调用多遍。`get_stock_info` 可在后续深层基本面阶段显式调用,不承担第一层业务归属补齐。
- **重工具必须有内部硬边界**:`get_stock_info`、`get_market_capital_flow`、`search_comprehensive_intel` 等慢工具不能只依赖 runner 外层 30s;工具内部需在自身预算内返回 `partial|timeout|error` 和 `source_chain/errors`,Trace 要能看出是哪个数据源慢,而不是统一显示 `Tool execution timed out after 30.00s`。
- **失败显式可见**:工具超时/异常写入 `facts.<tool>.status=failed|timeout`、`data_quality.failed_tools`、trace JSON,不做隐藏 fallback。
- **模型输入必须压缩但事实不能缺失**:席位 prompt 只能读取 `compact_seed_fact_packets_for_model(...)` 生成的模型输入版 `SeedFactPacket`,禁止把原始 `facts.<tool>.data`、大块 `tool_calls` 或 raw payload 塞回 LLM。压缩只能删工具外壳、传输日志、source_chain、完整 raw K 线等低价值内容;必须保留影响判断的股票事实,包括位置分位/乖离/RSI、结构摘要、支撑压力、趋势强度、均线关系、量能、资金 1/5/10 日、板块和基本面摘要。trace 可保留紧凑事实摘要,但席位上下文必须以 `status/summary/errors/data_quality` 为主,避免单票事实包把首轮 LLM 调用拖到超时。
- **席位保留少量工具权**:席位可以补证,但定位变为"补缺口/复核冲突/本席位关键二次确认",不是重新从零取全套数据。
- **不提前判断买卖**:`SeedFactPacket` 只陈述事实和数据质量,不能写 support/watch/oppose,不能替席位做结论。

### 0.5.2 business_context:宽口径业务/主题上下文

`SeedFactPacket` 必须在进入席位前补一层 `business_context`,用于回答"这只票属于什么业务/主题、和当日新闻/板块是否可能有关"。这层不是买卖判断,也不是精确硬编码的 `business_tags` 过滤器;它只把可复用线索显式交给后续席位和 Meta-Agent,避免席位只看到高位/超买而完全漏掉业务催化。

构建来源按宽口径合并:

- `get_stock_business_context.industry/boards/business_summary`:轻量业务归属工具,只补名称、行业、概念/板块和业务线索摘要,不拉估值、财报、资金、龙虎榜等深层基本面。
- `get_stock_info.belong_boards` / `boards`:兼容旧输入;后续更适合放在深层基本面或质量席补证,不作为 SeedFactPacket 默认业务归属来源。
- `FeatureFlag.summary/metrics`:召回阶段已经出现的新闻、板块、事件、策略线索。
- `FactSheet.sector_name/sector_strength`:本地或在线板块上下文。

输出字段保持克制:

| 字段 | 语义 | 约束 |
|---|---|---|
| `broad_industries` | 宽行业/业务簇,例如 `电子器件/元器件`、`电力能源`、`资源金属` | 只做宽归类,不把 MLCC、PCB、AI 服务器等细主题当唯一行业 |
| `board_names` | 原始板块/概念名及来源 | 保留少量原始名字,供模型判断直接/间接受益 |
| `theme_clues` | 新闻/事件/召回摘要中的主题证据 | 只陈述 evidence,不写 support/watch |
| `confidence` | `high/medium/low` | 来自 `belong_boards` 且有板块名为 high;只有 flags/fact_sheet 为 medium/low |

示例:风华高科如果只给出 `MLCC` 会太窄,下游容易漏掉"被动元件/电子元件/AI 服务器物料价值量提升"这类同一交易线索;正确表达应类似:

```jsonc
{
  "broad_industries": ["电子器件/元器件"],
  "board_names": [{"name": "电子元件"}, {"name": "被动元件"}, {"name": "MLCC"}],
  "theme_clues": [{"evidence": "MLCC 概念活跃,AI 服务器需求推动高端被动元件"}],
  "confidence": "high"
}
```

### 0.6 四席位怎么判断:四个完整打法,不是四个数据维度

四席位都读取同一批 `FeatureRow + FactSheet + SeedFactPacket`,但各自按不同打法筛选子集、输出不同 setup。大部分通用工具数据已在 `SeedFactPacket` 层统一取好;席位工具调用只用于补缺口和复核关键矛盾。`theme_catalyst_desk` 是消息主题的 precision 层,不是额外召回层;它只判断已进入 seed/recall 的主题票是否“催化真实 + 业务匹配 + 资金或板块验证”。

| 席位 | 输入偏好 | 核心问题 | 主要工具 | 输出 setup | 典型输出意见 |
|---|---|---|---|---|---|
| `early_turn_desk` 低位启动席 | 低位、形态、价量、资金初步转强 | "是否跌透后刚出现转强,且仍未透支?" | `analyze_price_structure`、`calculate_ma`、`get_volume_analysis`、`analyze_trend`、`get_capital_flow`、`get_market_capital_flow`、`get_symbol_regime_probability` | `early_turn` | `support`:低位平台放量转强;`watch`:位置低但转强证据不足;`oppose/invalid`:下跌中继或假突破 |
| `momentum_desk` 动量席 | 涨停、资金、强趋势、强板块 | "强势延续是否健康,资金承接是否真实,有没有追高风险?" | `get_capital_flow`、`get_tushare_moneyflow_dc`、`get_tushare_limit_step`、`get_stockapi_limit_up_pool`、`get_tushare_dragon_tiger_*`、`get_sector_rankings`、`get_board_capital_flow`、`get_symbol_regime_probability` | `trend_continuation` / `capital_momentum` | `support`:趋势健康且有回踩位;`watch`:强但过热需等分歧;`oppose`:高位拥挤/诱多 |
| `quality_repair_desk` 质量修复席 | 基本面、估值、低位/滞涨 | "业绩或景气是否改善,价格是否还没充分反映?" | `get_tushare_daily_basic`、`get_tushare_financial_indicators`、`get_tushare_forecast`、`get_tushare_express`、`get_stock_disclosure_events`、`get_capital_flow`、`analyze_price_structure`、`get_symbol_regime_probability` | `quality_repair` | `support`:业绩改善且估值未透支;`watch`:改善证据不完整;`oppose`:价值陷阱或已透支 |
| `theme_catalyst_desk` 主题催化席 | `news_theme_daily`、强板块、业务主题、资金验证 | "盘前/当日主题是否真实落地到这只票,且不是追在情绪末端?" | `get_eastmoney_cjzc_daily`、`get_stock_business_context`、`get_stock_disclosure_events`、`get_stockapi_hot_sectors`、`get_stockapi_sector_constituents`、`get_stockapi_sector_flow_history`、`get_capital_flow`、`search_comprehensive_intel`、`search_openinvest_news`、`get_symbol_regime_probability` | `theme_catalyst` | `support`:主题明确且业务/资金验证;`watch`:主题强但需等分歧/资金确认;`oppose`:泛概念、澄清负面或已透支 |

席位输出统一用 `ExpertPacketV2`:

```jsonc
{
  "expert": "early_turn_desk",
  "dimension": "early_turn",
  "status": "ok",
  "candidates": [
    {
      "code": "600000",
      "stance": "support",
      "setup_type": "early_turn",
      "reason": "低位平台放量站回关键均线,但需观察回踩不破",
      "evidence": [
        {"tool": "analyze_price_structure", "summary": "..."},
        {"tool": "get_volume_analysis", "summary": "..."}
      ],
      "risks": [
        {"type": "fake_breakout", "summary": "放量失败缩回平台则论点失效"}
      ]
    }
  ],
  "rejected": [
    {"code": "600001", "reason": "位置不低且 RSI 过热"}
  ],
  "diagnostics": []
}
```

席位输出的核心不是"分数",而是:

- `stance`:本席位态度,`support/watch` 才进入聚合候选。
- `setup_type`:告诉深挖后面该按哪套打法继续查。
- `reason`:本席位入池论点。
- `evidence`:本席位实际调用工具得到的证据。
- `risks`:本席位认为论点失效的条件。
- `rejected`:被本席位看过但不认可的样本,用于 Trace 排障。

### 0.7 四席位输出往后传给谁:聚合层先收敛,下游再决策

四席位输出不会直接进入最终报告,中间必须经过 `aggregate_desk_picks(...)` 和 `allocate_slots(...)`:

| 环节 | 输入 | 做什么 | 输出给谁 |
|---|---|---|---|
| `aggregate_desk_picks` | 四个 `ExpertPacketV2` + 原始 `FeatureRow` | 合并同票多席位意见;确定 `primary_desk`;用工具覆盖率算 `confidence`;打 `conflict_flags`;标 `multi_desk_conviction` | `allocate_slots` |
| `allocate_slots` | `AggregatedPool` + `MarketRegime` | 按市场状态给四席位分名额;防守市禁止动量;不足额按规则回填 | `candidate_discovery.candidates` |
| `candidate_screening` | L1 candidates + 证据包 | 初筛每只票是 `deep_dive`、`monitor` 还是 `reject` | 单股深挖/报告 |
| `single_stock_deep_dive` | `setup_type`、`fact_sheet`、席位 evidence、`conflict_flags` | 按打法 playbook 补证据并裁决冲突 | Meta-Agent |
| `meta_orchestrator` | 四席位报告 + 深挖摘要 + `MarketRegime` | 提取事实共识/策略分歧;给资产打 regime tag;把反对派风险转成硬约束;列出必算场景 | 点位计算层 |
| `pricing_agent` | Meta 场景与约束包 + 实时行情/ATR/盘口 | 不再判断"能不能买",只计算 If-Then 条件单矩阵 | `portfolio_allocation` |
| `portfolio_allocation` | Meta 摘要 + 点位矩阵 + 账户约束 | 规划组合动作、首仓比例、入场条件、止损条件和复查触发 | `adversarial_review` |
| `adversarial_review` | 候选、约束包、条件单、组合规划 | 反向审查,找证据缺口、约束遗漏和风控风险 | `judge_decision` |
| `judge_decision` | 全部上游结论 + 反方审查 | 最终裁决,输出采纳/修改/等待/拒绝 | 最终报告渲染 |
| `final.md` | 各 stage 已落盘 JSON | 确定性渲染 Meta 链路、入场区间、止盈止损和风险说明 | 用户 |

最终传给下游的候选字段应让读者能反查完整链路:

```jsonc
{
  "code": "600000",
  "name": "示例股票",
  "candidate_source": "thesis_desk_committee",
  "primary_desk": "early_turn_desk",
  "desks": ["early_turn_desk", "quality_repair_desk"],
  "stance": "support",
  "stance_by_desk": {
    "early_turn_desk": "support",
    "quality_repair_desk": "watch"
  },
  "setup_type": "early_turn",
  "reason": "低位启动席入池理由",
  "confidence": 0.75,
  "multi_desk_conviction": true,
  "conflict_flags": [],
  "llm_expert_evidence": {
    "early_turn_desk": [{"tool": "analyze_price_structure", "summary": "..."}],
    "quality_repair_desk": [{"tool": "get_tushare_daily_basic", "summary": "..."}]
  },
  "risks": [{"type": "fake_breakout", "summary": "..."}]
}
```

### 0.8 一个股票从入池到最终报告的例子

```text
600000 被 AlphaSift + Sequoia 召回
  -> FeatureRow.flags = [alphasift:strategy_match, sequoia:breakout]
  -> FactSheet 显示 range_pct_120=0.28, volume_ratio=1.8, trend_state=bullish
  -> momentum_desk: support, setup_type=trend_continuation, 证据=形态/量能/趋势
  -> early_turn_desk: watch 或不选,原因=低位结构不再作为默认入池主依据
  -> quality_repair_desk: 不选,原因=无基本面改善证据
  -> aggregate: primary_desk=early_turn_desk, confidence=工具覆盖率, conflict_flags=[]
  -> allocate: 根据 regime 给低位席名额,进入 L1 candidates
  -> candidate_screening: 判断是否进入 deep_dive
  -> deep_dive: 按 early_turn playbook 检查"低位+转强+失败条件"
  -> Meta-Agent: 抽取四席位共识/分歧,生成顺势/衰竭/回归三套约束
  -> 点位计算层: 只按约束计算条件单区间、止损与触发条件
  -> judge: 结合账户与风控,给出等待回踩确认/条件入场/拒绝等最终结论
```

这个例子说明:一只票可以因为"低位启动"进入候选,即使资金还没有强流入;动量席不支持也不等于否决,除非 FactSheet 或后续证据触发明确红线。

基本面:`get_tushare_daily_basic, get_tushare_financial_indicators/statements, get_tushare_forecast, get_tushare_express, get_tushare_dividend`
消息/事件:`get_eastmoney_cjzc_daily, get_tushare_today_news, score_stock_news_sentiment, search_comprehensive_intel, search_stock_news, get_tushare_announcements, get_tushare_stock_alerts, discover_event_impact, discover_news_momentum`

工具结果判读必须区分三类情况,不能在 Trace 或下游 prompt 里混写成"没搜到":
- `empty`:接口或搜索链路正常执行,但指定窗口内没有可用记录。例如 `get_tushare_announcements` 返回 `status=empty` 时,必须同时暴露 `date_window`。
- `partial-null`:数据源返回了行,但核心数值字段缺失。例如 `get_northbound_capital_flow` 的历史日期存在但 `net_inflow/buy_amount/sell_amount` 全为 `null`,必须在 `data_quality.core_numeric_available=false` 和 `warnings` 中显式标注,不得当成北向资金证据。
- `error/timeout`:工具请求失败或内部硬超时。必须保留 `source_chain/errors` 或 `error`,不得用空数组伪装成正常无数据。

`score_stock_news_sentiment` 的 `news_count>0` 只代表搜索/公告源有原始材料;只有 `event_tags/events/risk_flags` 命中时才代表规则引擎识别到公司级硬事件。`news_count>0` 且 `events=[]` 的正确解释是"有相关新闻,但没有硬事件",不是工具没搜到。

`get_sector_rankings` 是 Agent 快路径板块证据:优先读取 Tushare `ths_hot(market=行业板块)` 的同花顺行业板块热榜,返回行业板块热度排名、涨跌幅、当前价、热度值和采集时间等字段;东方财富 `stock_board_industry_name_em` 背后的行业板块实时行情与 StockAPI `/v1/hotBkJlrDr` 仅作为降级来源。所有来源失败时,直接返回 `failed/timeout` 与具体 `source_chain/errors`;禁止再进入 AkShare/Efinance/DataFetcherManager 慢速轮询把整轮拖到外层 30s timeout。

## 1. 召回层(特征库)— Layer 0 重写

**定位**:输入全市场,输出"带特征标签 + 廉价指标"的股票清单。只做事实标注、硬排除、去重、粗筛(按特征命中数 / 流动性),**绝不排序、不打优劣分**。

### 1.1 策略降级为特征探测器

把 `_build_seed_pool_result` 内每个主 source(daily_screener / capital_flow_anomaly / dragon_tiger / alphasift / sequoia / low_base / news_theme_daily / ...)的产物从"候选 + signal_score"改为"**给股票贴 FeatureFlag**"。同一只票被多个探测器命中 → 合并 flags,不再因此"加分"。

新数据结构(放 `schemas.py`):

```python
class FeatureFlag(BaseModel):
    detector: str          # "alphasift:high_tight_flag" / "moneyflow_dc" / "limit_step" ...
    kind: Literal["pattern","capital","limit","fundamental","position","sector","news"]
    summary: str           # 客观事实一句话:"放2.1倍量突破20日高点"

    coarse_drop_reason: str = ""
```

**召回源 → FeatureFlag 映射表(P3 落地依据,detector key 命名规范 `{source}:{signal}`):**

| Source | Detector key | kind | 典型 summary 模板 | metrics 关键字段 |
|---|---|---|---|---|
| daily_screener | `screener:ma_breakout` | pattern | "放{vr}倍量突破{n}日高点" | `volume_ratio`,`break_days` |

### 1.2 粗筛(可,但不排序)

- **硬排除**(沿用 `_passes_hard_exclusion` + `_local_daily_hard_exclusion_reason`):ST/退市/停牌/流动性下限(`LOCAL_HARD_EXCLUSION_MIN_AVG_TURNOVER`)。
- **粗筛保量**:按"命中特征数 ≥1 且通过硬排除"保留;若总量超过 `RECALL_COARSE_CAP`(默认 120,进 config),按"特征命中数"降序截断 —— 注意这是**命中数**(事实),不是优劣分。命中数相同则保留全部不再细排。
- **"不排序"与 cap 截断的边界澄清**:`RECALL_COARSE_CAP` 是**召回完整性的安全阀,不是优劣排序**。命中数只是"被几个探测器同时注意到"这一客观计数,不代表"更好";它仅用于在极端超量时决定**保谁不保谁**,不决定下游名次(下游名次由席位内 rank + regime 名额定)。理想情况 cap 不触发;一旦触发要记 `selection_recall` 诊断(截断了多少、命中数分布),便于回看 cap 是否设太低误砍。命中数处于截断边界(并列)时**全保**,宁可略超 cap 也不在事实层做优劣裁剪。
- 去重沿用 `_dedupe_by_code`,但合并 flags 而非"先到先得丢弃"。

### 1.3 召回层不再产出 `priority_score` 排序

删除跨源 `priority_score` 比较与 `_compress_seed_priority_score` 的"排序"用途(可保留为某 detector 的内部 metric,但不进全局排序)。**根治"跨源不可比"**:召回层根本不输出全局顺序。

当前实现的兼容约束:

- `SeedItem.priority_score` 可保留为 source 内部去重、截断和日志诊断字段。
- 写给 Trace / Web 的 `seed_pool_summary.preview[]` 只展示最多前 20 条 seed 的 `source_diagnostics`,不展示统一分数；完整 seed 数量以 `seed_count` 为准，后续四席位会处理完整 seed 池而不是只处理 preview。
- `_seed_to_candidate_payload()` 不再生成 `signal_score/score/priority_score/score_label/score_note`;候选页只能展示后续 `candidate_screening` 等真实评估分。

## 2. 共享事实底表 + 看空红线否决门 — "共识"住在这

### 2.1 FactSheet(确定性,每只票算一次,只陈述事实)

新增 `src/agent/candidate_experts_v2/fact_sheet.py`,函数 `build_fact_sheet(code, market, tool_registry, daily_df) -> FactSheet`。优先用召回阶段已加载的本地日线(`get_daily_history`/SQLite)算,避免重复网络调用。

```python
class FactSheet(BaseModel):
    model_config = ConfigDict(extra="allow")
    code: str
    # 资金(确定性,来自 get_capital_flow / moneyflow_dc,缺失填 unknown)

    trend_state: Literal["bullish","neutral","bearish","unknown"] = "unknown"
    breakdown_accelerating: bool = False          # 红线候选:有效跌破关键支撑且加速下跌
    range_pct_60: Optional[float] = None          # 60日区间分位 0-1
    range_pct_120: Optional[float] = None
    dist_to_high_20: Optional[float] = None       # 距20日高点 %
    gain_5d: Optional[float] = None               # 近5日涨幅 %
    bias_ma20: Optional[float] = None             # 距MA20乖离 %
    volume_ratio: Optional[float] = None          # 量比
    rsi14: Optional[float] = None
    # 流动性 & 硬风险
    avg_turnover_20: Optional[float] = None
    liquidity_ok: bool = True
    hard_risk_flags: List[str] = []               # st/delist/suspended/litigation/...
    # 板块/题材(共享上下文,替代独立题材席)
    sector_name: str = ""
    sector_strength: Literal["strong","neutral","weak","unknown"] = "unknown"
    sector_rank_pct: Optional[float] = None
    leader_already_up: Optional[bool] = None      # 板块龙头是否已涨(补涨判断用)
    freshness: str = "unknown"
    warnings: List[str] = []
```

`range_pct/bias/rsi/volume_ratio/gain_5d` 复用 `analyze_price_structure`/`calculate_ma`/`get_volume_analysis` 的算法或直接本地计算(旧方案要求的"位置元数据"全部归并到这里,**只算一次**)。

**字段取数优先级与缺失语义(section B):**
- `capital_direction`:优先 `get_capital_flow`(Tushare moneyflow 失败时可回退 StockAPI codeFlow),缺失再退 `get_tushare_moneyflow_dc`,再缺 → `unknown`。`moneyflow_ths` 当前因权限不足暂不作为主链路工具。
- **`unknown` 不等于看空**:资金 `unknown`/`neutral` 时,低位席**允许 support**(干净低位本就资金未进);只有 `outflow` + 放量(`capital_violent_outflow`)才进红线。这是非对称共识的关键落点。
- `trend_state`/位置类全部用本地日线确定性计算,日线缺失才 `unknown`。
- **freshness / 缓存分桶**:`intraday_bucket` 定义为交易时段每 30 分钟一桶(`09:30-10:00`=b1 … 收盘后=`eod`);FactSheet 缓存 key=`{code}:{date}:{intraday_bucket}`,非交易时段统一落 `eod` 桶。

**两阶段计算(控成本 + 不被网络拖垮):**
- **Phase A(纯本地,无网络)**:对**全部召回 row** 算,只用本地日线(SQLite)+ 已有 seed signals → 位置/趋势/量比/乖离/RSI/流动性/硬风险。这一阶段绝不发网络请求,保证 120 票也秒级完成。
- **Phase B(在线 enrich,按需)**:只对**进入 desk 子集或最终 Top 候选**的票补在线字段(如 `capital_direction` 走 moneyflow、`sector_strength` 走板块接口)。不对全量 120 票发网络请求。
- **网络失败非阻断**:Phase B 任一数据源失败 → 对应字段填 `unknown` 并写入 `warnings` + `source_chain`,**绝不阻断**召回/席位主流程(沿用 `data_provider` fallback 精神)。`capital_direction=unknown` 不杀低位(见上)。

### 2.2 看空红线否决门(确定性,非对称共识的"否决"侧)

新增 `src/agent/candidate_experts_v2/veto_gate.py`:`apply_veto(rows_or_picks) -> (kept, vetoed)`。红线**只看 FactSheet 事实**,与席位无关:

```python

    # ("breakdown_accelerating", True),                  # 破位加速下跌
```

- `hard_risk_flags` 非空 → 直接 veto(这条确定,无需用户定阈值)。
- `capital_violent_outflow` / `breakdown_accelerating` 的**判定阈值留 TODO 占位**(config key 见第 8 节),默认先设为"永不触发"以免误杀,等用户给实战阈值再开启。
- veto 结果是**确定性、可审计**的(记录 vetoed code + reason),不进 LLM。
- **执行位置:前移到席位之前**(`FactSheet → veto → 席位`)。硬红线在 FactSheet 里已确定,先 veto 能省 LLM 成本、避免席位在必死票上浪费 tool budget。因软红线默认不触发,前移阶段实际只拦 `hard_risk_flags`,**不会误杀低位票**;待用户给阈值开启软红线后,误杀风险仍由"永不触发→保守阈值"的渐进开启来控制。

> 非对称核心:红线只做"否决",**绝不存在"必须资金流入/技术看多"这种看多确认门**。低位票资金中性/微弱照样通过,只有"夺路出逃"才被拦。

```
- 多次试探同一压力位但回落收敛、下方有横盘换手 = 加分(吸筹);反复冲高失败长上影 = 否决。

【setup 标注】所有 pick 标 setup_type=early_turn。
【失败条件(每个 pick 必写)】跌回平台下沿 / 放量失败后缩回 / 资金回流仅一天无持续 / 板块与个股拐点不共振。
【主要警惕】抄在下跌中继、假突破。低位本身不构成理由——必须"低位证据 + 转强证据 + 失败条件"三者齐备。
```

## 4. 席位汇总:否决门 + 冲突打标 + 席位内排序(不打跨席位统一分)

新增 `aggregate_desk_picks(packets, rows) -> AggregatedPool`,替换 `_committee_candidate_score`/`_sort_committee_candidates`/`_merge_*_evidence` 的"共振加分"逻辑。**三件确定性的事,不做加权融合:**

1. **合并 pick → 候选**:被 ≥1 席位 pick(support/watch)的 row 进 L1;未被 pick 的进观察池(`status=observe`,不进深挖)。
2. **否决门已前移**(见 §2.2):硬红线在席位之前已 veto,此处不再重复;仅当用户后续开启软红线阈值时,可在此做一次"事实复核"二次确认(默认 no-op)。
3. **冲突打标**:pick 的论点与 FactSheet 矛盾 → 打 conflict flag,**不静默保留**,带标记下沉给深挖裁决。冲突类型枚举:

   | conflict flag | 触发条件 | 下沉处理 |
   |---|---|---|
   | `capital_thesis_mismatch` | 动量席标 capital_momentum,但 `capital_direction=outflow` | 深挖 capital_momentum playbook 必须裁决资金真实性 |
   | `thesis_position_mismatch` | 低位席标 early_turn,但 `range_pct_120` 处高位(>阈值) | 深挖 early_turn playbook 复核"是否真低位" |
   | `trend_thesis_mismatch` | 延续/动量论点,但 `trend_state=bearish` | 深挖复核趋势结构 |
   | `quality_price_mismatch` | 质量席标 quality_repair,但价格已大涨(估值透支信号) | 深挖复核"价格滞后"是否成立 |

4. **confidence(确定性,落地"工具覆盖率替换 LLM confidence")**:
   `confidence = 已被工具 evidence 覆盖的关键维度数 / 本席位期望维度数`。**dimension ↔ tool 映射**(放 manifest 或 config,每席一张):

   | desk | expected_dims | dimension ← tool |
   |---|---|---|
   | early_turn_desk | position, volume, trend, capital | position ← analyze_price_structure/calculate_ma;volume ← get_volume_analysis;trend ← analyze_trend;capital ← get_capital_flow |
   | momentum_desk | trend, volume, capital, structure | trend ← analyze_trend;capital ← get_capital_flow/moneyflow_dc;structure ← limit_step/dragon_tiger;volume ← get_volume_analysis |
   | quality_repair_desk | earnings, valuation, position | earnings ← financial_indicators/forecast/express;valuation ← daily_basic;position ← analyze_price_structure |
   | theme_catalyst_desk | theme, business, sector, capital, position | theme ← get_eastmoney_cjzc_daily/search_stock_news;business ← get_stock_business_context;sector ← hot_sectors/hot_sector_leaders;capital ← capital_flow/volume;position ← realtime_quote/analyze_price_structure |

   - 同一维度多工具命中**只计 1 次覆盖**(分子是"被覆盖的维度数",不是工具数)。
   - 工具返回 `unknown`/数据不足 **不算覆盖**(但 capital 维度 `unknown` 不视为席位失败,见 §2.1)。
5. **多席位同选同一票(方向一致)** = 真共识 → 标 `multi_desk_conviction=True`,**提高深挖优先级**(注意:这与旧"共振加分"不同,是两套独立打法不约而同,不是一票六维都亮)。
   - **primary_desk 归属**(allocate 名额计入哪个席位):取 stance 更强者(support>watch),并列取 confidence 更高者,再并列按 config 的席位优先序(默认 `early_turn > quality_repair > momentum`,体现低吸优先)。`setup_type` 以 primary_desk 的标注为准。一张选票只占一个席位名额,避免重复计数。
6. **席位内排序**:每席位内部按 `(multi_desk_conviction, confidence, 关键 metric)` 排序,各交 Top N(N 进 config,默认 5);**不产出跨席位全局分**。allocate 时即以各席位的这份内部排序为准取名额。

`AggregatedPool` 结构:
```python
class AggregatedCandidate(BaseModel):
    model_config = ConfigDict(extra="allow")
    code: str; name: str = ""; market: str = "cn"
    setup_type: CandidateSetupTypeV2
    desks: List[str] = []                  # 哪些席位选了它
    stance_by_desk: Dict[str,str] = {}
    confidence: float = 0.5                # 工具覆盖率算出

class AggregatedPool(BaseModel):
    by_desk: Dict[str, List[AggregatedCandidate]] = {}   # 席位内已排序

    observe: List[AggregatedCandidate] = []
    regime: str = "unknown"
    diagnostics: List[Dict[str,Any]] = []
```

## 5.5 Meta-Agent / Orchestrator:资产定性与场景约束包

### 5.5.0 定位:只做"定性编排",不做"点位计算"

Meta-Agent 是四席位之后、点位计算层之前的一层**决策编排器**。它的职责不是再选一次股票,也不是直接给入场价、止盈价或"买入/卖出"指令,而是把四席位的主观判断和反对意见整理成下游可执行的**资产定性 + 硬约束 + 必算场景**。

核心边界:

- **定性解耦**:Meta-Agent 只判断"当前是什么行情、这只票属于什么流派机会、分歧在哪里",不输出具体入场点位/止盈点位。
- **约束传递**:反对派席位提出的风险,必须转成下游点位计算层必须遵守的数学边界,例如结构破坏位、均线锚点、最大追高溢价、论点失效条件。
- **多场景并行**:Meta-Agent 必须要求点位计算层至少计算顺势突破、假突破衰竭、均值回归三套 If-Then 剧本,避免单一路径乐观化。
- **不覆盖四席位**:它不替代 `aggregate_desk_picks` / `allocate_slots`;四席位仍负责候选是否进入 L1,Meta-Agent 只处理已进入深挖/点位计算的候选。

### 5.5.1 输入:四席位报告 + 深挖摘要 + 市场环境

Meta-Agent 的输入必须是压缩后的结构化上下文,不直接塞全量工具 raw JSON:

```jsonc
{
  "stock": {"code": "600027", "name": "华电国际", "market": "cn"},
  "desk_reports": {
    "early_turn_desk": {"stance": "watch", "reason": "...", "risks": [], "evidence": []},
    "momentum_desk": {"stance": "support", "reason": "...", "risks": [], "evidence": []},
    "quality_repair_desk": {"stance": "oppose", "reason": "...", "risks": [], "evidence": []},
    "theme_catalyst_desk": {"stance": "support", "reason": "...", "risks": [], "evidence": []}
  },
  "deep_dive_summary": {
    "setup_type": "trend_continuation",
    "thesis_check": {"verdict": "confirmed", "why": "..."},
    "conflict_resolution": [],
    "entry_plan": {
      "candidate_anchor_levels": [
        {"name": "BOS支撑", "price": 5.25, "source": "momentum_desk"},
        {"name": "MA20", "price": 5.21, "source": "deep_dive"}
      ],
      "failure_condition": "放量跌破BOS支撑且资金撤离"
    }
  },
  "fact_sheet": {},
  "seed_fact": {},
  "market_context": {
    "regime": "trending_up | range_bound | risk_off | panic | unknown",
    "volatility_bucket": "low | normal | high | extreme",
    "risk_level": "low | medium | high",
    "position_guidance": "..."
  }
}
```

输入压缩规则:

- 席位报告只保留 stance/reason/evidence/risks/关键价格锚点,不传整段 prompt 对话。
- `market_context` 优先来自 `detect_market_regime`;如果大盘数据 `data_quality=insufficient`,Meta-Agent 必须降低结论强度并保留 `market_context_warnings`。
- `deep_dive_summary.entry_plan` 中的点位可以作为**候选锚点**,但 Meta-Agent 不能把它们改写成最终入场价;最终点位仍由点位计算层结合 ATR/盘口/实时价计算。

### 5.5.2 工作流:共识/分歧 → 市场过滤 → 约束包

**Step 1:识别共识与分歧**

Meta-Agent 先把四席位报告拆成两类:

| 类型 | 说明 | 示例 |
|---|---|---|
| 事实共识 | 多个席位或工具共同确认的客观事实 | "120日高位分位91%"、"近5日涨幅8.38%"、"均线多头排列"、"主力资金近5日净流入" |
| 策略分歧 | 不同打法对同一事实的解释差异 | 动量席认为突破有效;低位/质量席认为位置过高、存在衰竭风险 |

然后给股票打 `asset_regime` 标签。标签不是买卖结论,只是告诉下游这只票的主导矛盾:

| asset_regime | 含义 | 下游关注 |
|---|---|---|
| `Right_Side_Momentum_High_Exhaustion_Risk` | 高位右侧动量,但衰竭风险高 | 严格计算突破延续与假突破两套条件 |
| `Early_Turn_Low_Base_Confirmation` | 低位启动,等待确认 | 重点计算回踩不破和转强确认 |
| `Quality_Repair_Price_Not_Fully_Reflected` | 质量修复,价格未完全反映 | 重点计算价值修复的容错区间 |
| `Theme_Follow_Breadth_Dependent` | 板块补涨,依赖板块扩散 | 重点计算板块退潮失效条件 |
| `Avoid_By_Market_Regime` | 大盘环境禁止做多 | 点位计算层可只生成观察/失效说明,不生成开仓条件单 |

**Step 2:市场环境过滤器**

Meta-Agent 必须把个股论点放进 `MarketRegime` 中重新解释:

| 市场场景 | 逻辑 | Meta 动作 |
|---|---|---|
| 牛市/主升/情绪高涨(`trending_up`) | 强者恒强,高位突破更可能延续 | 放大 `momentum_desk` 权重;左侧恐高降级为次级风险,但仍保留止损约束 |
| 震荡/存量博弈(`range_bound`/`high_volatility`) | 高位突破容易诱多,低吸与质量更占优 | 放大低位/质量席警告;动量突破必须附带更严格回踩确认 |
| 风险偏好下降(`risk_off`/`panic`/`trending_down`) | 做多信号胜率显著下降 | 一票否决主动追高;输出 `asset_regime=Avoid_By_Market_Regime` 或要求点位计算层只算观察/防守剧本 |
| 未知(`unknown`) | 数据不足,不应强行乐观 | 保守处理;所有顺势剧本必须降级为条件触发 |

**Step 3:生成场景与约束包**

Meta-Agent 必须把席位意见翻译成点位计算层能直接读取的硬约束:

- 从动量席提取结构破坏位,例如 BOS 支撑、突破位、趋势线。
- 从低位/反转席提取均值回归锚点,例如 MA20、平台下沿、前低。
- 从质量席提取估值/过热限制,例如最大追高溢价、估值透支警告、业绩证伪条件。
- 从反对意见提取 `risk_constraints`,不得只写成自然语言提醒。

### 5.5.4 与点位计算 / 组合规划 / 反方审查 / Judge / 报告的衔接

```text
四席位 JSON + 深挖摘要 + MarketRegime
  -> Meta-Agent
  -> scenario_constraint_package.json
  -> 点位计算层
  -> if_then_order_matrix.json
  -> 组合规划
  -> 反方审查
  -> Judge
  -> final.md
```

职责边界:

- **Meta-Agent**:回答"这只票属于什么资产机会、分歧在哪里、哪些边界不能破、下游必须算哪些场景"。
- **点位计算层**:回答"在这些硬约束下,结合实时价/ATR/盘口/涨跌停规则,If-Then 条件单怎么写"。内部 stage key 仍为 `pricing_agent`,用于兼容历史 trace 和 JSON 消费方。
- **组合规划**:回答"在账户约束下,哪些条件单可以进入组合计划、首仓比例是多少、什么时候复查"。
- **反方审查**:回答"组合规划有没有违反 Meta 硬约束、点位矩阵是否缺失败场景、证据缺口是否足以降级"。
- **Judge**:回答"最终采纳、修改、等待更多数据还是拒绝本轮建仓"。
- **最终报告**:不是 LLM stage。它由代码读取已落盘的 stage JSON 确定性渲染,不再补写新证据或重新判断股票。
- **最终报告表头与正文同源**:核心结论表拆成"机会首选/执行首选/可观察标的"三类。`机会首选` 来自逐股深挖、Meta 约束和点位计划共同支持的主线机会,不因账户过于谨慎而被抹掉;`执行首选` 来自组合规划 `positions_plan.rank` 下的可执行或条件触发计划,必须受账户、市场和风控约束;未进入深挖的候选只能放入"观察池"或附录候选池,不能进入表头核心结论,避免表头与后续章节像两套独立排序。
- **Meta 链路展示不是推荐排序**:`Meta-Agent` 专章只解释四席位、Meta 约束包和点位计算层如何对齐正文主线标的。若正文已有深挖/组合规划标的,Meta 链路不得再从 pricing/package 里补展示其它股票;只有正文主线为空时才允许 fallback 展示其它链路包。标题必须显式标注为链路对齐/非推荐排序,不得使用 `### 1. 股票` 这类容易被误读为推荐顺位的标题。

运行时调用顺序是串行的,后一层只能读取前一层已经写入 `SelectionRunContext.stages` 的 JSON:

| 顺序 | stage | 是否 LLM 调用 | 主要输入 | 主要输出 | 传给谁 |
|---|---|---|---|---|---|
| 1 | `meta_orchestrator` | 是,1 次 | 四席位报告、深挖摘要、`MarketRegime` | `summary` + `full.packages[]`:资产定性、硬约束、必算场景 | 点位计算层 |
| 2 | `pricing_agent` | 是,1 次 | `meta_constraint_packages`、最近行情/深挖锚点、账户上下文 | `if_then_order_matrix`:每只股票的 If-Then 条件单矩阵 | 组合规划 |
| 3 | `portfolio_allocation` | 是,1 次 | Meta 摘要、压缩约束包、条件单矩阵、账户约束 | `positions_plan`:动作、仓位、入场/止损/复查条件 | 反方审查 |
| 4 | `adversarial_review` | 是,1 次 | 候选证据、Meta/点位矩阵、组合规划、证据账本 | 反方论点、证据缺口、需要修改的计划 | Judge |
| 5 | `judge_decision` | 是,1 次 | 组合规划、反方审查、Meta/点位约束、市场环境 | 最终动作、裁决摘要、下一步 | `final.md` 渲染 |
| 6 | `final.md` | 否 | 各 stage JSON、推荐列表、证据摘要 | Markdown 报告 | 用户 |

因此从 Meta 到 Judge 是 **5 次顺序 LLM stage 调用**;`final.md` 是确定性报告渲染。若任一 stage 返回 `partial`/`insufficient_data`,下游必须把缺口带下去并降级,不能用后续 LLM 偷偷补成"看起来完整"。

点位计算层的禁止项:

- 不重新判断"这只股票能不能买"。
- 不覆盖 `hard_constraints_for_pricing_agent`。
- 不把 Meta 的 asset_regime 当作买入建议。
- A 股场景下默认不生成真实做空执行单;`Fakeout_Exhaustion` 只生成退出/回避/风险提示,除非系统未来显式支持融券或指数对冲。

### 5.5.5 Meta-Agent System Prompt 框架

```text
# Role
你是一个量化投资组合经理(Meta-Agent / Orchestrator)。你的任务是审阅来自不同交易流派(动量、低位启动、质量修复)的专家席位报告,并结合大盘环境,为下游"定量点位计算系统"提供资产定性与硬性约束包。

# Core Rules
1. 绝不越权:禁止输出具体入场点位、止盈点位,也禁止输出强倾向的"建议买入/卖出"结论。
2. 吸收反对派价值:反对席位提出的风险警告,必须转化为下游必须遵守的数学边界,例如结构破坏位、均线锚点、最大追高限制、论点失效条件。
3. 强制多场景:必须要求下游同时计算"顺势突破"、"假突破衰竭"、"均值回归"至少三个场景。
4. 市场环境优先:如果 MarketRegime 为 risk_off/panic/trending_down,不得强化追高或主动做多语义。
5. JSON only:严格输出指定 schema,不要输出 Markdown 或解释性长文。

# Workflow
1. 提取 4 个席位报告中的客观事实共识与主观策略分歧。
2. 结合 Market Context 判定资产主导流派(asset_regime)。
3. 从席位报告和深挖摘要中提取关键价格锚点,组成 hard_constraints。
4. 生成 required_pricing_scenarios,交给点位计算层计算 If-Then 条件单。

# Input Data
- Desk Reports: {4个席位JSON}
- Deep Dive Summary: {单股深挖摘要}
- Market Context: {detect_market_regime输出}

# Output Format
严格输出 selection_meta_orchestrator JSON schema。
```

### 5.5.6 Trace 与报告消费

- 新增 artifact:`meta_orchestrator_{code}.json`,保存完整场景与约束包。
- Trace 事件:`selection_meta_orchestrator`,字段包括 `code`、`asset_regime`、`market_regime`、`required_scenarios_count`、`hard_constraints_count`、`status`。
- 最终报告主文必须面向 Meta-Agent 链路重排,而不是只把 Meta 摘要塞进辅助审查:
  - 先展示"四席位 → Meta-Agent → 点位计算层 → 组合规划 → 反方审查 → Judge"链路,说明每只票经过哪些席位、谁支持/反对/观察。
  - 显式解释 `meta_analysis.factual_consensus`、`strategic_divergence`、`asset_regime`、`hard_constraints_for_pricing_agent`、`required_pricing_scenarios`、`if_then_order_matrix` 的字段语义。
  - 每只进入报告的股票必须展示入场区间、止盈目标、止损/失效条件;如果点位计算层/深挖没有给出,直接写"缺失",不补假点位。
  - 报告股票数量控制在 1-5 只;默认深挖 4 只,真实排障可临时降到 1 只。
- 如果 Meta-Agent `status=insufficient_data`,点位计算层仍可生成防守/观察场景,但 Judge 不得输出强开仓。
- `final.md` 只做渲染,不能新增未出现在 stage JSON 中的入场价、止盈价、新闻事实或席位意见。

## 7. 深入探究重写 — setup playbook 路由(Layer 2)

### 7.0 本层目标:把"选股深挖"从通用个股分析 prompt 里拆出来

当前需要补齐的最后一层不是再做一次"全市场选股",也不是复用 `planning_prompts.py` 里的账户通用分析,而是专门处理**四席位已经选出来的 L1 候选**:

```text
四席位候选入池榜 candidates
  -> candidate_screening 初筛
  -> selection_deep_dive_targets 选择 1-3 只
  -> 选股专用 single_stock_deep_dive prompt
  -> deep_dive_results.json
  -> 最终报告逐股深挖段 + allocation/adversarial/judge
```

拆分原则:

- `planning_prompts.py` 只保留规划 Agent / 通用账户任务的系统规则,不再承载选股深挖细节。
- `stock_selection_prompts.py` 或后续独立的 `stock_selection_deep_dive_prompts.py` 承载选股流水线专用 prompt。
- `position_review` / `entry_analysis` 的单票分析可以有自己的 prompt,但不得和 `watchlist_scan` 的候选深挖共用一套长 prompt。
- 选股深挖只分析**已经被四席位和初筛放行的候选**,不新增候选、不替换股票、不做最终组合仓位。

推荐文件边界:

```text
src/agent/planning_prompts.py
  # 只管任务识别、规划、账户通用行为边界

src/agent/stock_selection_prompts.py
  # 保留 candidate_discovery / candidate_screening / allocation / adversarial / judge
  # 可继续导出 build_deep_dive_prompt 作为兼容入口

src/agent/stock_selection_deep_dive_prompts.py
  # 新增:选股候选专用深挖 prompt
  # build_selection_deep_dive_prompt(payload)
  # build_selection_deep_dive_batch_summary_prompt(payload)  # 可选,只做汇总不做逐股裁决

src/agent/stock_selection_meta_prompts.py
  # 新增:Meta-Agent / Orchestrator prompt
  # build_meta_orchestrator_prompt(payload)
```

### 7.1.1 深挖目标选择:最多 3 只,最少 1 只

本层的目标不是覆盖所有 L1 候选,而是把报告时间花在最值得解释的 1-3 只上。

**硬规则:**

- `SELECTION_DEEP_DIVE_MIN=1`:只要候选发现和初筛没有全失败,最终至少深挖 1 只,否则报告只能给"本轮无可深挖候选"。
- `SELECTION_DEEP_DIVE_MAX=3`:最多深挖 3 只,避免整轮选股被单股长分析拖慢。
- 初筛明确 `reject` 的候选不得因为补足 1 只而进入深挖;如果全被 reject,深挖结果为空,报告明确说明"四席位候选全部被初筛淘汰"。
- `pool_fallback` 可以用于补足最少 1 只或丰富报告,但必须标记 provenance,不能伪装成已通过初筛。

推荐选择顺序:

1. `candidate_screening.full.shortlist` 中 `screening_result=deep_dive` 的候选,按初筛分/候选池顺序取。
2. 若不足 1-3 只,补 `screening_result=monitor` 但未被 reject 的候选。
3. 若仍不足最少 1 只,按 `candidate_discovery.candidates` 的席位名额顺序补 `pool_fallback`。
4. 同一股票只深挖一次;多席位共选只作为 `multi_desk_conviction` 提升优先级,不重复占名额。

排序权重建议:

```text
deep_dive_priority =
  screening_result(deep_dive > monitor > pool_fallback)
  + primary_desk quota order
  + multi_desk_conviction
  + confidence(tool coverage)
  - conflict_penalty(有冲突但未裁决)
  - provenance_penalty(pool_fallback)
```

### 7.1.2 调用方式:默认 3 次 1 只,不建议 1 次塞 3 只

推荐默认执行方式是**每只股票独立一次深挖 prompt**,最多 3 次:

```text
for code in deep_dive_targets[:3]:
    evidence = reuse_balanced_evidence_or_collect(code)
    prompt = build_selection_deep_dive_prompt(one_candidate_payload)
    result = call_llm(stage_name=f"single_stock_deep_dive:{code}")
combine_deep_dive_outputs(results)
```

原因:

- 三只股票可能来自不同 `setup_type`(低位启动/动量/质量修复),单个 prompt 更容易走对 playbook。
- 单股 JSON schema 更稳定,不会出现模型把 A 股证据写到 B 股上的串票问题。
- 单只失败、超时或数据缺口可以单独降级,不会污染另外两只。
- 报告天然需要逐股小节;单股 artifact 也方便 Trace 展开。

效率控制不靠"把 3 只塞进一个 prompt",而靠:

- 深挖上限固定为 3。
- 优先复用 `balanced_candidate_evidence`、`FactSheet` 和席位 evidence,只补缺口。
- 每只 deep dive 设置独立 timeout,失败只降级该股票。
- 证据收集可并行;LLM 调用可保守串行,若后续成本可控再改为最多 2-3 并发。

`1 次 3 只`只作为可选 batch 模式,适用条件很窄:

- 不允许模型再调用工具,所有逐股证据都已收集完毕。
- 三只股票 `setup_type` 相同或高度相近。
- 只做**报告摘要压缩**,不做逐股裁决。

因此当前设计建议:

```text
默认: 3 x single-stock prompt
```

### 7.1.6 六类 playbook 与四席位关系

四席位传来的 `setup_type` 决定深挖 playbook:

| primary_desk | setup_type | 深挖核心 | 报告重点 |
|---|---|---|---|
| `early_turn_desk` | `early_turn` | 低位是否真低、转强是否成立、是否不是下跌中继 | "低位启动条件"、回踩确认、失效平台 |
| `momentum_desk` | `trend_continuation` | 趋势是否健康、是否过热、是否有舒服回踩位 | "强势延续但不追高"、回踩位、禁追线 |
| `momentum_desk` | `capital_momentum` | 资金承接是否真实、连板/龙虎是否诱多 | "资金接力质量"、分歧转一致、破板风险 |
| `quality_repair_desk` | `quality_repair` | 基本面改善是否真实、估值是否透支、价格是否滞后 | "质量修复逻辑"、业绩证伪条件 |
| `theme_catalyst_desk` | `theme_catalyst` | 主题催化是否真实、业务是否匹配、资金/板块是否验证、是否已透支 | "主题催化链路"、产业链角色、资金验证、退潮风险 |
| 任意席位 | `theme_follow` | 板块强度是否传导到个股,是否只是纯跟风 | "补涨有效性"、板块退潮风险 |

`unknown` 只作为保守兜底。长期目标是四席位候选都必须带 `setup_type`;否则 Trace 需要标记为 `setup_type_missing`。


### 7.2 五套 playbook(判定内核,内嵌进 prompt)

| setup | 核心论点(必须证伪) | 必查证据 | 入场 | 止损(价格) | failure_condition(论点证伪,可非价格) |
|---|---|---|---|---|---|
| early_turn | 拐点成立且未透支 | 低位+首次转强+资金由负转正 | 回踩不破平台/放量确认 | 平台下沿/启动低点 | 资金回流仅一天、放量失败缩回、跌回平台 |
| trend_continuation | 趋势健康、有回踩位、未追高 | 趋势结构+均线多头+乖离/RSI检查+回踩位 | 回踩MA/突破回踩 | 突破位/趋势线 | 量价透支、次日大幅分歧、趋势破坏 |
| capital_momentum | 资金承接真实非诱多 | 主力净流入持续性+龙虎结构+封板强度+连板高度 | 竞价/分歧转一致 | 破封板成本/首板低点 | 开板、诱多、资金次日撤离 |
| quality_repair | 业绩/景气改善且估值未透支、价格滞后 | 盈利质量/亏损收窄+估值位置+景气+价格滞后 | 偏价值、容忍慢 | 基本面逻辑破坏 | 业绩证伪、估值已透支、景气逆转 |
| theme_follow | 板块强且个股为有效补涨 | 板块强度+龙头已涨/二线未涨+资金流向二线 | 板块回踩企稳 | 板块走弱 | 纯跟风、板块见顶 |

### 7.3 顺手修的 3 个老问题
- **failure_condition vs stop_loss 解耦**:每 playbook 明确二者定义(failure=论点证伪、可非价格;stop_loss=价格风控),prompt 要求两者都给并解释差异。
- **证据复用**:REUSED_EVIDENCE_BLOCK 注入 fact_sheet + 席位 evidence,指令"已有数据的维度只补缺口/过期项,不重复全量取证"。
- **市场逻辑剥离**:涨停/龙虎/北向进 `MARKET_BLOCK[cn]`,港美各自 block。

### 8.3 性能 / 并发 / 降级
- 召回 + FactSheet 全确定性,**本地 SQLite 优先**,FactSheet 每票只算一次(下游全程复用)。
- SeedFactPacket 在席位前并行构建,默认对 `AGENT_SEED_POOL_TOTAL_LIMIT=32` 个 seed 跑 `analyze_price_structure/analyze_trend/calculate_ma/get_volume_analysis/get_capital_flow/get_stock_business_context` 等通用工具;同一 seed 的同一工具只跑一次,四席位共享。`get_stock_business_context` 只做第一层业务归属,避免前置阶段为了 `belong_boards` 拉完整 `get_stock_info`。`AGENT_SEED_POOL_TOTAL_LIMIT` 控制进入四席位前的 seed 总上限,单票真实 smoke 或排障可临时设为 1-3;`AGENT_SEED_FACT_MAX_WORKERS` 控制全局并发,`AGENT_SEED_FACT_TOOL_TIMEOUT_SECONDS` 控制单工具超时。
- 4 席位并行(复用 `run_experts_parallel`),每席位只吃自己子集；席位内部按单只 seed/FeatureRow 顺序调用 LLM,不会把 20 只股票一次性塞进同一个 prompt。每次 LLM 工具调用显式使用 `AGENT_CANDIDATE_EXPERT_TIMEOUT_SECONDS`(默认 60s),避免继承 LiteLLM 长超时导致席位结果晚到；外层 seed wall-clock guard 按「首轮 LLM + 工具执行 + 二轮/三轮 LLM」留出完整余量,避免先于 LLM 硬超时误杀。
- LLM fallback 预算必须在候选模型之间预留,不能让首个慢模型独占完整 `AGENT_CANDIDATE_EXPERT_TIMEOUT_SECONDS`。例如有主模型 + fallback 两个模型时,首轮应给主模型保守子预算,主模型硬超时后仍要有剩余时间尝试 fallback；否则 trace 会出现 `timed out before trying fallback model ...`,并连续触发 `consecutive_seed_failures`,导致低位启动席/动量席整席空输出。

**成本预算量化上限(section,防失控):**
- 最坏情况:`RECALL_COARSE_CAP=120` 票 × 4 席位,若每票都跑 LLM 不可接受。靠三道闸控制:① veto 前移先砍硬红线;② 每席位只吃自己子集(典型每席 ≤ 30-40 票);③ 每席位 `max_tool_calls=10` 是**整席预算**,不是每票预算 —— 席位需在 prompt 里被告知"优先核实最像本打法的 3-6 只,而非全量"。
- 量化红线:席位 LLM 调用按"单 seed 单席位 loop"运行,但输入已经带 seed facts,目标是每只 seed 进入席位后 0-2 个补证工具;席位补证 tool 调用仍受 `max_tool_calls` 和 per-seed guard 限制。SeedFactPacket 工具调用单独进入 `selection_seed_facts.tool_status_counts/packets_preview` 和每票 compact facts,不混进席位 evidence,方便判断耗时到底发生在取数层还是席位层。
- FactSheet 工具调用走确定性本地优先,不计入席位 tool 预算;SeedFactPacket 的在线取数也不计入席位补证预算,但必须单独落 trace。

**失败契约(四席位是候选闸门,不做 seed fallback):**
- 某席位超时/报错 → 跳过,其余继续。
- **全部席位失败或 thesis desk 空输出 → 本轮候选发现失败**,`candidate_discovery.status=failed`,`candidate_discovery.candidates=[]`,`llm_expert_committee.fallback=false`。
  - seed pool 只保留为输入 provenance 和排障诊断,不得自动提升为 L1 候选。
  - stock_selection 主流程在候选发现阶段 fail-fast,不继续 screening/deep_dive/allocation,避免把未通过席位判断的 seed 包装成可深挖候选。
  - Trace 必须保留 `seed_pool_summary`、压缩后的 `seed_fact_packets`、`thesis_desk_packets`、`thesis_desk_packets[].per_seed_packets`、`thesis_desk_diagnostics`,前端据此展示每只 seed 的取数质量、每个席位、每只 seed 的真实输出/超时原因。
- 缓存:沿用 `cache.py` `seed_hash`,key 改 `{desk}:{market}:{date}:{rows_hash}`;FactSheet 按 `{code}:{date}:{intraday_bucket}` 缓存(分桶定义见 §2.1)。

| `selection_conflict_flags` | `code`,`flags`:[conflict key],`detail` |
| `selection_slot_allocation` | `regime`,`alloc`:{desk:n},`backfill`:[{from,to,n}],`final_codes` |
| `selection_desk_degraded` | `degraded`:bool,`reason`,`fallback_source` |

Trace 落盘硬要求:

- `seed_pool.json`:记录召回来源、硬排除、source quality、market regime。
- `seed_facts.json`:记录每只 seed 的模型输入版 compact `SeedFactPacket`,包括 `facts.<tool>.status`、错误、`summary` 和 `data_quality`;文件按紧凑 JSON 写入,不是给用户阅读的 pretty trace。禁止默认写入工具原始 `data`、大块 `tool_calls`、逐工具耗时或传输链路日志,避免 N 只 seed 传给下一个模型时撑爆上下文。这是判断"取数层缺/坏"的主证据;如需 raw payload 或逐工具耗时,只能作为单次人工 debug 产物另存,不得进入默认链路。
- `candidate_discovery.json`:保留候选发现完整 payload,其中必须包含 `seed_fact_summary` 和压缩后的 `seed_fact_packets`。
- `events.ndjson`:必须出现 `selection_seed_pool_built`、`selection_seed_facts`、`selection_seed_gate_done` 或候选发现失败事件,用于前端逐步展示。
- `summary.json`:最终必须给出 artifact_dir,方便用户从页面或文件系统打开整轮 trace。

所有事件挂在现有 trace 通道,供 `AgentTracePage` 展示。

### 12.1 切默认前的量化验收(Trace 观测,opt-in 跑够样本再改默认)
新模式设默认前,需在 shadow/opt-in 运行中达到:
- **低位席候选占比**:`early_turn` setup 候选在 L1 中占比达到预期区间(对照旧模式应**显著上升**,印证低吸保护生效)。
- **防守市动量=0**:`risk_off`/`panic`/`trending_down` regime 下,动量席候选数严格为 0(回填未破坏禁动量护栏)。
- **degraded 比例**:`selection_desk_degraded=true` 占比 ≤ 阈值(如 <5%),否则说明席位稳定性不足,不切默认。
- **性能**:平均 discovery 耗时、总工具调用数在预算内(LLM ≤3×5、tool ≤30,见 §8.3)。
- **新旧候选重合率 + 差异样例**:抽样核对新模式剔除/新增的票是否符合"低吸优先、不追高"预期。
- **稳定性**:至少 N 次(如 ≥20)连续 trace **无 schema/JSON 解析失败**。

任一项不达标 → 保持 opt-in,不改默认。
